# `2_20:40→47`：三轮本机对照计时

本报告只解释一个已查看过的开发案例。动作判断在测量前保存于 [2_20-premeasurement.md](2_20-premeasurement.md)，机器可读汇总见 [code-credit-2_20-summary.json](code-credit-2_20-summary.json)。原始逐次计时和源码快照在本机忽略目录 `runs/ada-2_20-valid-r{0,1,2}.json` 及各自 `.assets/` 中。

## 实际做了什么

使用现有 KernelBench 入口和同一块 RTX 5060 Laptop GPU，沿用 5 次正确性、30 次计时的工作量，依次使用顺序种子 200、201、202。父版本、子版本、只恢复 `clone().detach()` 的版本、只恢复 `BLOCK=128` 的版本在三轮都通过正确性检查。所有比较都在子版本其余代码保持不变的条件下进行。

首次父子核对记录 `runs/ada-2_20-screen-0925.json` 因 Triton 尝试写入无权限的用户缓存目录而双双报错；这是环境错误，没有作为代码错误或计时证据。将 `TRITON_CACHE_DIR` 指向项目 `.cache/triton` 后重跑，父子通过，记录为 `runs/ada-2_20-screen-0925-cachefix.json`。正式三轮也使用该缓存设置。

| 轮次 | 父版本 ms | 子版本 ms | 子版本恢复复制 ms | 子版本恢复 BLOCK=128 ms |
| --- | ---: | ---: | ---: | ---: |
| 200 | 19.53 | 15.01 | 18.20 | 15.06 |
| 201 | 19.57 | 15.02 | 18.22 | 15.09 |
| 202 | 19.55 | 15.02 | 18.20 | 15.05 |

父子延迟比三轮分别为 1.301、1.302、1.301，中位约 **1.30 倍**。在子版本中恢复完整复制，每轮都比子版本慢约 3.2 ms，条件效应 `log(T_without/T_child)` 中位为 **0.1926**。这支持“省去这次设备复制确实帮助当前子版本提速”，但不能把父子速度差按比例分给这一行：其他 kernel 与启动变化仍在，且可能与复制选择互相影响。

仅恢复 `BLOCK=128` 时，三轮分别慢约 0.046、0.066、0.022 ms，对数效应中位 **0.0031**。原始样本的波动与这个差别接近，且本例没有合格的普通可执行代码对照。因此记录为 **未判定**；汇总 JSON 的 `measured` 仅说明生成了数值，不能读成确认了优化贡献。

预备的 `without-kernel_group.py` 含未定义的 `x_ptr`，并没有完整恢复所需的参数及启动连接。它未进入这三轮，状态为 **构造无效 / 共同动作待测**。本例也没有普通可执行代码对照，不能据此估计误报率或声称定位方法优于差异分块。

## 对研究问题的意义和限制

旧规则把 `clone().detach()` → `detach()` 标为普通代码；这次独立撤销与重复计时说明它在该例是一个真实的性能漏报。旧规则也漏掉 `BLOCK` 变化，但这次不足以说明该变化有稳定贡献。一个确认的漏报值得保留为方法失败证据，不应再按此例加关键词后宣称定位更准。

这轮只补上一个困难案例中的局部因果证据。它没有完整验证 kernel 共同动作，没有普通可执行对照、任务留出集或真实生成 token，更没有学习结果。下一步按冻结的筛查顺序寻找其他真实修改，累计完整的成功、失败与未判定记录。
