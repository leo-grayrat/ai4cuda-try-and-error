# 信用分配先导实验

2026-09-24，在本机 NVIDIA GeForce RTX 5060 Laptop GPU 上，用 KernelBench 的 `eval_kernel_against_ref` 验证四份实际 CUDA 候选。题目是本仓库的 KernelBench 格式向量加法；A 表示每线程处理两个元素，B 表示 block size 从 128 改到 256，AB 同时采用两项修改。三轮运行改变了候选评测顺序，每轮每候选保存 30 个 CUDA Event 延迟样本；四份候选在每轮均通过上游 5 次正确性检查。

以 `J = -log(候选延迟中位数)` 计，三轮结果如下：

| 轮次 | A 的单独贡献 | B 的单独贡献 | A×B 交互项 |
|---|---:|---:|---:|
| 原顺序 | -0.01149 | -0.00339 | +0.00416 |
| 顺序种子 1 | -0.00029 | -0.00049 | -0.00552 |
| 顺序种子 2 | -0.00019 | +0.00058 | -0.00078 |

交互项方向不稳定，幅度也很小。这组数据 **没有** 支持“组合结构造成明显非加性收益”的主张。它证明的是受控四版本实验、原始计时保存与重复运行比较已可执行。下一步应从真实优化轨迹中筛选两项能独立构造的结构修改，在归约、融合或共享内存等更可能产生交互的任务上重测，并与轮间波动比较。

本机原始 JSON 与源代码快照保存在被 Git 忽略的 `runs/kernelbench-add-rtx5060-raw.*`、`runs/kernelbench-add-rtx5060-order-1.*` 和 `runs/kernelbench-add-rtx5060-order-2.*`。实验清单与四份候选源码在 `experiments/kernelbench-add/`。上游 KernelBench 修订：`423217d9fda91e0c2d67e4a43bf62f96f6d104f1`。

计时口径是上游 KernelBench 的 CUDA Event 围住整个 `ModelNew.forward` 调用；每次计时前，上游会用一个大张量冲刷 L2 缓存。记录中的延迟因此是这个评测口径下的冷缓存候选调用，不宜直接解释成单条 CUDA kernel 指令的纯执行时间。评测时没有持续采集 GPU 时钟和功耗，不能把后续跨轮差异归因到某个确定的硬件状态。

## 第二题：逐行求和

同日又在 4096×1024 的 float32 逐行求和上运行四版本实验。A 每线程每轮读取相邻两个元素，B 将每行线程数从 128 改为 256，AB 同时施加两项修改。三轮分别按原顺序、顺序种子 1、顺序种子 2 运行；每轮每候选保存 30 个 CUDA Event 样本，四个版本均通过五次正确性检查。源代码和清单位于 `experiments/kernelbench-row-sum/`，原始记录位于忽略版本控制的 `runs/row-sum-rtx5060-{0,1,2}.json` 及对应快照。

| 轮次 | A 的单独贡献 | B 的单独贡献 | A×B 交互项 |
|---|---:|---:|---:|
| 原顺序 | -0.03608 | -0.00171 | +0.00116 |
| 顺序种子 1 | 0.00000 | -0.00114 | +0.00085 |
| 顺序种子 2 | +0.00171 | +0.00142 | +0.00000 |

A 在第一轮看似降低性能约 3.5%，后两轮却与基线几乎相同。三轮交互项均很小，不能据此主张组合优化存在稳定收益。这进一步显示：对几十微秒量级的 kernel，单轮中位数差异可能大于待解释的交互项，归因前必须保留重复运行与原始样本。这两题的改动由本仓库为方法验证而构造，**不是现成 Agent 优化轨迹**，也不能代表多题研究结论。

随后为了验证完整快照重放，又用同一清单、同一 GPU 和保存的评测器运行两轮。两轮 B 的贡献约为 -0.032，交互项分别为 +0.01776 和 +0.03024；这与先前三轮的接近零结果不一致。源码、参考实现、上游修订和适配器哈希均相同，四个候选均通过正确性检查。此次差异没有定位到唯一原因；不能把较早三轮或较晚两轮单独挑出来作为性能结论。原始记录为 `runs/row-sum-snapshot-source.json` 和 `runs/row-sum-snapshot-replay.json`。快照重放验证的是 **代码与流程可重现**，并不保证微秒级计时数值相同。
