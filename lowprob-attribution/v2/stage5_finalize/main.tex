\hypertarget{token-probability-distributions-in-multi-turn-gpu-kernel-generation}{%
\section{Token Probability Distributions in Multi-Turn GPU Kernel
Generation}\label{token-probability-distributions-in-multi-turn-gpu-kernel-generation}}

\textbf{Author:} leo-grayrat \textbf{Affiliation:} Independent research
\textbf{Date:} 2026-10-18

\hypertarget{abstract}{%
\subsection{Abstract}\label{abstract}}

CUDA Agent attributes an early reinforcement-learning collapse to a
distribution mismatch associated with the rarity of CUDA in pretraining.
Its explanation connects that rarity to token probabilities near
\(10^{-9}\), which would amplify small differences between training and
rollout probabilities. We examine the proposed connection through
per-token measurements collected during multi-turn kernel generation.

The main experiment comprises 128 runs on four elementwise or reduction
tasks and 40 runs on five KernelBench Level 2 operator chains, yielding
98,533 and 542,611 tokens, respectively. CUDA/Triton vocabulary has a
low-probability rate of 0.26\% under a strict vocabulary definition,
compared with 0.84\% for other tokens. In the operator-chain collection,
the rate is 0.60\% inside code blocks and 13.56\% outside them;
excluding comments reduces the code rate to 0.33\%. The lowest observed
code-token probability is approximately \(2.2\times10^{-6}\) across
322,375 code tokens. Contextual inspection places the main contributions
to the low-probability tail in comments, identifier naming, punctuation
and malformed continuations. The inspected examples provide no clear
instance of uncertainty between alternative kernel implementations.

These observations locate the probability cost primarily in the
surrounding prose and surface form of the generated output.
Failure-following responses account for 87.5\% of the operator-chain
tokens, making the composition of the interaction an important part of
this distribution. A supplementary audit recovers 40 code-bearing tool
arguments with probabilities for 3,162 generated tokens, demonstrating
collection through the local tool-call interface alongside the
reply-body route used in the main experiment.

\textbf{Keywords:} CUDA Agent; training instability; conditional
probability; log-probability distribution; fusion kernels

\hypertarget{introduction}{%
\subsection{1. Introduction}\label{introduction}}

\hypertarget{the-claim}{%
\subsubsection{1.1. Training instability and the vocabulary
explanation}\label{the-claim}}

Multi-turn reinforcement learning has enabled language models to develop
GPU kernels through repeated implementation, evaluation and revision, as
demonstrated by Kevin and CUDA Agent \citep{kevin, cudaagent}. In its
main KernelBench table, CUDA Agent reports an overall pass rate of
98.8\% and a faster-than-\texttt{torch.compile} rate of 96.8\% across
250 workloads \citep{cudaagent, kernelbench}. Its training procedure
uses proximal policy optimisation (PPO) over trajectories produced in a
development sandbox \citep{cudaagent, ppo}.

The authors report that their first run collapsed after 17 training
steps. They attribute this instability to a severe domain distribution
mismatch, citing a CUDA share below 0.01\% of pretraining data and token
probabilities near the numerical floor \citep{cudaagent}. The
illustrative probability in their explanation is

\[
\pi_\theta(a_t\mid s_t)\approx10^{-9}.
\]

Here the action is the generated token and the state is its preceding
context. At such a small denominator, a difference between the training
and rollout probabilities could produce a large importance ratio:

\[
\rho_t(\theta)=\frac{\pi_\theta(a_t\mid s_t)}
{\pi_{\theta_{\mathrm{old}}}(a_t\mid s_t)}.
\]

The proposed remedy combines single-turn reinforcement learning,
rejection fine-tuning on positive-reward trajectories and value
pretraining of the critic. The explanation therefore links the
composition of the pretraining corpus to a particular feature of the
generated-token distribution, and then connects that feature to training
instability.

\hypertarget{selection-of-the-second-link}{%
\subsubsection{1.2. Token-level measurement of the proposed
mechanism}\label{selection-of-the-second-link}}

The proposed mechanism contains four steps: CUDA is rare in pretraining;
that rarity produces near-floor token probabilities; those probabilities
amplify precision differences in the importance ratio; and the resulting
instability causes training to collapse. Each step concerns a different
observable and calls for a corresponding measurement.

The second step can be examined by collecting conditional token
probabilities during generation. This makes it accessible through an
inference interface and allows the vocabulary explanation to be tested
before undertaking a training run. We measure where low-probability
tokens occur, inspect the code surrounding them, and compare the
observed tail with the magnitude quoted by CUDA Agent. These
measurements provide an empirical check on the distributional premise of
the proposed mechanism.

\hypertarget{measurement-constraints}{%
\subsubsection{1.3. Measurement
constraints}\label{measurement-constraints}}

The DeepSeek API responses inspected during setup returned probabilities
for reply text and reasoning, while code written inside tool-call
arguments lay outside those returned fields. For the main experiment, we
therefore asked the model to place its candidate implementation in the
reply body. A driver wrote the file, ran the evaluator and returned
feedback for the next turn.

The saved local vLLM records expose a complementary interface. With
Qwen3-4B-AWQ, the generated probability stream includes serialised tool
calls and the code strings inside their arguments. Concatenating this
stream in generation order makes it possible to recover the code and
associate its spans with the recorded probabilities. Section 4.8 reports
the evidence obtained through this route.

\hypertarget{design-of-this-study}{%
\subsubsection{1.4. Design of this study}\label{design-of-this-study}}

The main experiment measures conditional token probabilities in a
multi-turn kernel-writing loop using two task families. Family A
contains four elementwise or reduction tasks, and Family B contains five
KernelBench Level 2 operator chains. The analysis addresses four
questions:

\begin{itemize}
\tightlist
\item
  \textbf{RQ1:} How does the low-probability rate of CUDA/Triton
  vocabulary compare with that of other tokens?
\item
  \textbf{RQ2:} How does the distribution differ between fenced code and
  surrounding prose?
\item
  \textbf{RQ3:} How does the code-side rate vary across the selected
  reduction and operator-chain tasks?
\item
  \textbf{RQ4:} How close are the observed token probabilities to the
  quoted floor?
\end{itemize}

We also inspect low-probability tokens in their original contexts to
determine whether they occur at implementation decisions, identifier
choices, comments or other parts of the output.

\hypertarget{summary-of-results}{%
\subsubsection{1.5. Summary of results}\label{summary-of-results}}

The vocabulary comparison places fewer low-probability tokens in the
CUDA/Triton group than in the remainder of the output. The regional
comparison shows a much larger separation between code and prose, which
becomes more pronounced when comments are removed from the code region.
Across the selected tasks, code-side rates remain low, and the measured
code-token minimum stays above the quoted floor. The table summarises

\hypertarget{scope}{%
\subsubsection{1.6. Scope}\label{scope}}

The main collections describe the inference-time output of an aligned
commercial model, while CUDA Agent's explanation concerns a base model
during training rollout. The comparison examines whether the proposed
vocabulary effect appears in the measured output distribution. Section
5.2 discusses how model state enters the interpretation, and the local
records extend the collection method to code generated through tool
calls.

\hypertarget{related-work}{%
\subsection{2. Related Work}\label{related-work}}

\hypertarget{the-causal-chain-under-test}{%
\subsubsection{2.1. The causal chain under
test}\label{the-causal-chain-under-test}}

CUDA Agent connects domain rarity, near-floor token probabilities and
training instability, then uses staged warm-up to stabilise PPO
\citep{cudaagent}. Rejection fine-tuning retains positive-reward
trajectories and removes unsuccessful or malformed interactions. Value
pretraining uses generalised advantage estimation \citep{gae}, and
subsequent PPO training uses asymmetric clipping \citep{cudaagent, ppo}.
The settings reported for these components are collected below
\citep{cudaagent}:

\begin{center}
\begin{minipage}{\linewidth}
\centering
\begin{tabular}{@{}llr@{}}
\toprule
Component & Parameter & Value \\
\midrule

Advantage estimation & Discount factor & 1 \\
Advantage estimation & Trace-decay factor & 0.95 \\
PPO clipping & Lower bound parameter & 0.2 \\
PPO clipping & Upper bound parameter & 0.28 \\
\bottomrule
\end{tabular}
\end{minipage}
\end{center}

CUDA Agent's own ablations show reward collapse and rising policy
entropy when rejection fine-tuning is removed, and lower explained
variance with longer trajectories when value pretraining is removed
\citep{cudaagent}. These observations describe training behaviour at the
distribution and trajectory levels. The near-floor probability proposed
in the same paper concerns an individual generated token, motivating a
token-level measurement alongside the reported aggregate indicators
\citep{cudaagent}.

\hypertarget{dr-kernel-mismatch}{%
\subsubsection{2.2. Train/inference mismatch in DR.
KERNEL}\label{dr-kernel-mismatch}}

DR. KERNEL studies reinforcement learning for Triton kernel generation
and examines both training instability from train/inference mismatch and
an objective that can be misaligned with meaningful speedup
\citep{drkernel}. It monitors entropy, gradient norms and perplexity,
and applies geometric Mismatch Rejection Sampling to restrict the
discrepancy between training and rollout probabilities.

For a trajectory with token index set \(T\), the geometric-mean
importance ratio is

\[
w=\exp\left(\frac{1}{|T|}\sum_{t\in T}
\log\frac{\pi_{\mathrm{train}}(a_t\mid s_t)}
{\pi_{\mathrm{rollout}}(a_t\mid s_t)}\right).
\]

The acceptance interval is

\[
0.999\leq w\leq1.001.
\]

A further token-level veto rejects any sequence containing a likelihood
ratio below the specified threshold:

\[
\frac{\pi_{\mathrm{train}}(a_t\mid s_t)}
{\pi_{\mathrm{rollout}}(a_t\mid s_t)}<10^{-4}.
\]

DR. KERNEL reports that this procedure stabilises training dynamics
without fundamentally raising the performance ceiling \citep{drkernel}.
The result makes train/inference discrepancy an important comparison for
the vocabulary account: the two explanations locate the relevant
distributional difference in different parts of the generation and
training process.

\hypertarget{precision-mismatch-and-off-policy-drift}{%
\subsubsection{2.3. Precision mismatch and off-policy
drift}\label{precision-mismatch-and-off-policy-drift}}

Jet-RL studies the numerical discrepancy introduced when rollout uses
FP8 precision and training uses BF16, and proposes a unified precision
flow to stabilise optimisation \citep{jetrl}. Zheng et al.~derive a
first-order formulation of token-level policy-gradient objectives and
relate its validity to training--inference discrepancy and policy
staleness \citep{firstorder}. Yao et al.~demonstrate that separate
rollout and training backends can assign different token probabilities
even with shared model parameters, motivating importance-sampling
correction \citep{liuoffpolicy}.

Trust Region Masking extends this analysis to long-horizon reinforcement
learning by examining the sequence-level consequences of implementation
divergence and masking trajectories outside a trust region
\citep{trustregion}. Together, these studies motivate measuring the
probabilities that enter the importance ratio and identifying where
their tails occur \citep{jetrl, firstorder, trustregion}. Our experiment
supplies the generated-token distribution for selected kernel-writing
tasks, including its regional composition and contextual examples.

\hypertarget{logprob-availability-in-closed-apis}{%
\subsubsection{2.4. Logprob availability in closed
APIs}\label{logprob-availability-in-closed-apis}}

Probability outputs are useful scientific observations in their own
right. Chauvin et al.~use token log-probabilities to detect changes in
models served through APIs, showing that these measurements can support
low-cost monitoring \citep{logprobtracking}. Carlini et al.~recover
information about a production model's output projection through
black-box API access, illustrating the additional information exposed by
probability-related outputs \citep{carlini}.

The serving interface also determines which parts of a generated
interaction can be measured. Michaelov et al.~distinguish model
evaluation, comparison and interpretation as research goals with
different access requirements \citep{howopen}. In our DeepSeek
experiments, moving code into reply text made its probabilities
accessible. In the local vLLM records, the generated stream retained
both tool-call arguments and their probabilities. Recovering the latter
requires parsing the serialised output and locating the code within its
JSON strings. These collection routes make the measured output channel
explicit for each experiment.

\hypertarget{position-of-this-work}{%
\subsubsection{2.5. Position of this work}\label{position-of-this-work}}

The present study examines the generation-time distribution implicated
by the vocabulary explanation. Its contribution is a measurement across
two task families, supported by regional comparisons and contextual
reading of the tail. The accompanying local audit establishes how code
probabilities can also be recovered from tool arguments, extending the
observable interface available for such experiments.

\hypertarget{method}{%
\subsection{3. Method}\label{method}}

\hypertarget{collection-without-an-agent-framework}{%
\subsubsection{3.1. Collection without an agent
framework}\label{collection-without-an-agent-framework}}

The main experiment uses a driver to collect code directly from the
reply body. During setup, an instruction to print code before issuing a
tool call produced no compliant response in six trials. Moving file
writing and execution into the driver allowed the model's implementation
to remain within the API's returned probability fields throughout
collection.

For each task, the driver sends a description and \texttt{reference.py},
and requests a complete \texttt{candidate.py} inside a fenced block. It
extracts the block from \texttt{message.content}, writes the candidate,
invokes an independent evaluator and appends the evaluation output to
the conversation. A single-turn probe returned a 1,396-character code
block containing \texttt{@triton.jit} and \texttt{tl.load}; all 448
tokens within the block had a recorded log-probability. The local
collection uses the tool-call interface described in Section 3.5.

\hypertarget{the-loop}{%
\subsubsection{3.2. Generation and evaluation loop}\label{the-loop}}

At each turn, the driver submits the accumulated message history and
records the model's response together with its token probabilities. The
API request uses the following generation settings:

\begin{center}
\begin{minipage}{\linewidth}
\centering
\begin{tabular}{@{}lr@{}}
\toprule
Setting & Value \\
\midrule

\texttt{logprobs} & \texttt{true} \\
\texttt{top\_logprobs} & 20 \\
\texttt{temperature} & 1.0 \\
\bottomrule
\end{tabular}
\end{minipage}
\end{center}

Let \(M_t\) denote the message history at turn \(t\), and let \(y_t\)
denote the generated response. For token position \(i\), the recorded
value is

\[
\ell_{t,i}=\log\pi_\theta\!\left(y_{t,i}\mid M_t,y_{t,<i}\right).
\]

The driver extracts the candidate block and stages it with the reference
implementation and evaluator in an isolated temporary directory. After
running the evaluator, it appends the response and evaluation feedback
\(f_t\) to the history:

\[
M_{t+1}=M_t\oplus[\mathrm{assistant}:y_t]
\oplus[\mathrm{user}:f_t].
\]

Here the concatenation operator appends messages in order. A run stops
when a candidate passes after at least one revision, when the response
contains no fenced block, or when the turn limit is reached. The limit
is eight turns for the reduction tasks and six turns for the operator
chains.

\hypertarget{two-task-families}{%
\subsubsection{3.3. Two task families}\label{two-task-families}}

Family A contains \texttt{row\_reduce}, \texttt{vector\_affine},
\texttt{layernorm\_rows} and \texttt{softmax\_rows}. These tasks use
elementwise operations or single-dimension reductions, with short kernel
bodies and limited control flow. Family B draws five operator chains
from KernelBench Level 2, the operator-sequence split of a benchmark
containing 250 PyTorch workloads \citep{kernelbench}:

\begin{center}
\begin{minipage}{\linewidth}
\centering
\begin{tabular}{@{}ll@{}}
\toprule
Task & Chain \\
\midrule

\texttt{12\_gemm\_multiply\_leakyrelu} & Linear → scale → LeakyReLU \\
\texttt{1\_conv2d\_relu\_biasadd} & Conv2d → ReLU → bias \\
\texttt{14\_gemm\_divide\_sum\_scaling} & Gemm → divide → sum → scale \\
\texttt{17\_conv2d\_instancenorm\_divide} & Conv2d → InstanceNorm →
divide \\
\texttt{19\_convtranspose2d\_gelu\_groupnorm} & ConvTranspose2d → GELU →
GroupNorm \\
\bottomrule
\end{tabular}
\end{minipage}
\end{center}

The operator chains offer several implementation arrangements:

\begin{itemize}
\tightlist
\item
  A candidate can fuse the chain into one kernel.
\item
  It can fuse an elementwise tail into the epilogue of a heavy
  operation.
\item
  It can retain separate operations with intermediate tensors.
\end{itemize}

These arrangements introduce choices about fusion, intermediate storage
and tiling that broaden the implementation space represented in the
experiment. The script \texttt{scripts/make\_kb2\_tasks.py} adapts each
KernelBench \texttt{Model} class to the \texttt{run(x)} entry point. It
seeds the model so that the reference and candidate use identical
weights and exports the model as \texttt{MODEL} for the candidate to
import. Evaluators check correctness on two shapes with a tolerance of
\(10^{-4}\).

\hypertarget{feedback-conditions}{%
\subsubsection{3.4. Feedback conditions}\label{feedback-conditions}}

The experiment uses two feedback conditions to vary the amount of
evaluator output returned to the model:

\begin{itemize}
\tightlist
\item
  \textbf{Full feedback} returns the evaluator's verbatim output.
\item
  \textbf{Truncated feedback} returns one line containing
  \texttt{compilation\ failed}, \texttt{output\ mismatch} or
  \texttt{correct}.
\end{itemize}

Both procedures were implemented before collection and remained fixed
throughout the experiment. The condition therefore changes the returned
feedback while keeping the collection procedure consistent within each
task family.

\hypertarget{model-selection}{%
\subsubsection{3.5. Model selection}\label{model-selection}}

Model selection was tied to the available collection interface and
hardware. The main task families use a larger model through the DeepSeek
API, with code placed in reply text. The earlier local experiments use
Qwen3-4B-AWQ under vLLM on an 8 GB GPU and retain code in tool-call
arguments.

In the local records, \texttt{content\_logprobs} contains the generated
tokens of serialised tool calls, including proposed file contents. The
corresponding OpenCode events retain the tool names, input strings and
execution status. Recovering a code argument involves concatenating the
token stream, parsing the tool-call JSON and locating the
\texttt{content} or \texttt{newString} value. Some responses have empty
\texttt{content\_text} and \texttt{tool\_call\_text} convenience fields
even though their generated stream contains the code. Section 4.8
reports the audit of these saved records.

Families A and B use the non-reasoning API model with a maximum response
budget of 8,192 tokens. The reasoning variant tested during setup
exhausted a 4,000-token budget in the reasoning channel and returned an
empty content field with \texttt{finish\_reason=length}. The selected
interface made reply-body code probabilities accessible while allowing a
larger model than the local GPU could serve. This choice treats the API
as the measurement instrument and specifies its observable output
channel, following the distinction between model behaviour and
deployment access discussed by Michaelov et al. \citep{howopen}.

An earlier vocabulary comparison from the local collection was withdrawn
after a classification error was identified. Section 5.5 describes that
error; the retained records support direct inspection of the generated
code and its probabilities.

\hypertarget{observables}{%
\subsubsection{3.6. Observables}\label{observables}}

The analysis describes both the frequency and magnitude of
low-probability tokens. For each region or token group, it reports the
following quantities:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  The fraction of tokens below a fixed log-probability threshold.
\item
  The 0.1st, 1st, 5th and 50th percentiles of the log-probability
  distribution.
\item
  The minimum log-probability and its corresponding absolute
  probability.
\item
  The fraction of total negative log-probability contributed by the
  lowest-probability 0.1\%, 1\% and 5\% of tokens.
\end{enumerate}

For a token set \(G\), the threshold rate is defined as

\[
R_\tau(G)=\frac{1}{|G|}\sum_{i\in G}\mathbf{1}\!\left[
\log\pi_\theta(a_i\mid s_i)\leq\tau\right],
\qquad\tau=-2.
\]

The quantiles and minimum describe how far the tail extends, while the
concentration statistic in Section 4.5 describes how much of the total
cost it carries. Region assignment follows fenced-block state: tokens
following an odd number of opening or closing triple-backtick delimiters
are assigned to code, and the remaining tokens to prose. This regional
analysis uses the generated text's structure without a vocabulary
classifier.

\hypertarget{statistics}{%
\subsubsection{3.7. Statistics}\label{statistics}}

The vocabulary comparisons use a two-sided Fisher exact test on a
two-by-two table whose dimensions are group membership and whether the
token falls below the threshold. An exact test accommodates the
unbalanced cell counts in these comparisons. Tokens within a completion
are dependent, however, so token-level tests can overstate the precision
of the reported differences. We report their effect sizes alongside the
nominal significance values; the analysis does not include a run-level
cluster adjustment.

\hypertarget{concentration-of-probability-mass}{%
\subsubsection{4.5. Concentration of negative
log-probability}\label{concentration-of-probability-mass}}

To measure how much of a region's cost comes from its tail, we sum the
negative log-probabilities of its tokens:

\[
C(G)=-\sum_{i\in G}\log\pi_\theta(a_i\mid s_i).
\]

After sorting tokens by increasing log-probability, let \(G_q\) contain
the lowest-probability fraction \(q\) of the region. The concentration
statistic is

\[
\kappa_q(G)=\frac{C(G_q)}{C(G)}.
\]

A value of 0.981 at the 5\% cutoff means that those tokens contribute
98.1\% of the region's total negative log-probability. Applying the
statistic to Family B gives

prose & 220,236 & −179,942 & 1.4\% & 9.3\% & \textbf{30.3\%} \\

\hypertarget{discussion}{%
\subsection{5. Discussion}\label{discussion}}

\hypertarget{status-of-the-second-link}{%
\subsubsection{5.1. Vocabulary attribution in the measured
output}\label{status-of-the-second-link}}

The main observations place the low-probability tail outside the
vocabulary group highlighted by the domain-rarity explanation.
CUDA/Triton terms have a lower threshold rate than other tokens, and the
regional comparison places substantially more cost in surrounding prose.
Contextual inspection further associates much of the tail with comments,
names and malformed continuations.

Together, these results challenge the attribution of the measured
probability cost to CUDA vocabulary. The selected kernel-writing tasks
produce highly probable code continuations alongside a broader prose
distribution, and their code-token minimum remains above the quoted
floor. The distribution's dependence on output region provides a more
direct description of the observed variation than the domain label
alone.

\hypertarget{the-magnitude-gap-and-its-interpretation}{%
\subsubsection{5.2. The magnitude gap and its
interpretation}\label{the-magnitude-gap-and-its-interpretation}}

The observed code-token minimum is approximately four hundred times the
quoted floor, while the median code-token probability rounds to one.
This gap motivates examining how model state, generated context and
token selection enter the comparison. CUDA Agent discusses a base policy
during rollout, while our main collections use an aligned model through
an inference API \citep{cudaagent}. Chlenski et al.~examine cross-model
fidelity and find that agreement in predictions can coexist with
differences in attribution, making the measurement target and the kind
of inference important to specify \citep{surrogate}.

The empirical finding is that near-floor probabilities are absent from
the measured code output, including its CUDA/Triton vocabulary. To
connect this result to the training account, a matched base-model
measurement would locate the same quantities before fine-tuning and show
how their distributions change afterward. Such a comparison would
directly test whether the quoted tail is associated with the base policy
and how it relates to the vocabulary and regions identified here.

\hypertarget{regional-distribution-as-the-supported-finding}{%
\subsubsection{5.3. Regional distribution as the supported
finding}\label{regional-distribution-as-the-supported-finding}}

The largest separation in the measured distribution occurs between code
and prose. Under the fence rule, their threshold rates are 0.60\% and
13.56\%; removing comments lowers the code rate to 0.33\%. This
separation appears across all five operator-chain tasks, whose
individual code-side rates remain low even when evaluation success is
uncommon.

The contextual examples suggest an explanation for this pattern.
Familiar code sequences, such as a masked \texttt{tl.load}, strongly
constrain their continuations. Explanatory prose permits a wider range
of wording and punctuation, distributing probability across more
possible continuations. The concentration analysis reflects this
difference: the lowest-probability 5\% of code accounts for nearly all
its cost, while prose accumulates cost over a much broader part of its
token distribution.

The composition of the interaction also contributes to the aggregate
result. Failure-following responses contain most of Family B's tokens
and have a higher threshold rate than initial responses. Understanding
the generated distribution therefore requires tracking both the kind of
text produced and the evaluation context in which the model produces it.

\hypertarget{a-context-distribution-account-of-the-collapse}{%
\subsubsection{5.4. A context-distribution account of the
collapse}\label{a-context-distribution-account-of-the-collapse}}

The regional measurements motivate a hypothesis linking training
instability to the contexts generated during unsuccessful revision. CUDA
Agent reports rising entropy alongside reward collapse
\citep{cudaagent}, and DR. KERNEL finds that controlling train/inference
mismatch stabilises training \citep{drkernel}. Our collections place
much of the probability cost in prose produced around failed
evaluations. These observations suggest examining the distribution of
diagnostic and self-correction text encountered during rollout.

Under this hypothesis, failed evaluations lead the policy into contexts
containing compiler diagnostics, revised explanations and attempts to
recover from an unsuccessful implementation. Their continuation
distribution may differ from that represented in successful
demonstrations. Tracking how often training visits these contexts could
help explain changes in entropy and importance ratios as trajectories
lengthen.

Rejection fine-tuning offers a relevant comparison because it selects
successful trajectories and thereby changes the context mixture used to
anchor the policy \citep{cudaagent}. In our Family B collection,
success-following responses contain 12,147 tokens and failure-following
responses contain 474,728. These counts illustrate the potential size of
the mixture difference and motivate measuring its effect directly within
a training run.

A second explanation places the uncertain prose downstream of an
unresolved implementation problem. A struggling model may produce both
an incorrect kernel and a diffuse explanation, with the prose recording
the difficulty already present in the interaction. Distinguishing these
explanations requires interventions that vary the generated context
while holding other aspects of the task fixed.

Two comparisons would help. One could retain the content of a failure
message while changing its diagnostic formatting, then measure the
response distribution in code and prose separately. Another could
request a complete rewrite after a successful evaluation, providing a
comparison between rewriting after success and rewriting after failure.
Logging the same regional probabilities, entropy and importance ratios
during training would then connect these interaction-level measurements
to the discrepancy examined by Jet-RL and the objective analysis of
Zheng et al. \citep{jetrl, firstorder}.

\hypertarget{classification-bias-in-the-first-pass}{%
\subsubsection{5.5. Classification bias in the first
pass}\label{classification-bias-in-the-first-pass}}

The initial local-model analysis assigned a 10.00\% low-probability rate
to the \texttt{triton\_specific} class, with a nominal significance
value of 0.0156. Inspection revealed that the classifier's treatment of
\texttt{load}, \texttt{zeros} and \texttt{store} depended on the region
in which they appeared. To avoid labelling ordinary English as Triton
vocabulary, the rule only admitted certain occurrences inside code
segments. It consequently retained 20 of 451 relevant occurrences,
including two extreme samples.

with very different recorded rates:

\hypertarget{collection-driver-defect}{%
\subsubsection{5.6. Collection driver
defect}\label{collection-driver-defect}}

The collection driver contributed substantially to Family B's failed
evaluations. It accepted any fenced block as a candidate, including
fragments intended as local revisions. In 14 of 39 runs examined for
this defect, the model's last output contained a fragment of 63--239
characters; an example is
\texttt{group\_id\ =\ pid\ //\ (GROUP\_M\ *\ num\_pid\_n)}. Executing
such fragments as complete files produced 16 \texttt{NameError} failures
among the 32 failed evaluations in that breakdown.

Four additional failures arose from out-of-memory errors after the
task's peak memory use had been underestimated, and nine were output
mismatches. Excluding fragment runs gives a success rate of 28\% on
complete files, or seven of 25. The driver defect also increases the
number of failure-following responses in the collection, making it
relevant to the context mixture measured in Section 4.6.

\hypertarget{complementary-coverage-of-reply-text-and-tool-parameters}{%
\subsubsection{5.7. Complementary coverage of reply text and tool
parameters}\label{complementary-coverage-of-reply-text-and-tool-parameters}}

The two collection routes make code probabilities observable through
different output interfaces. In Families A and B, the model prints a
candidate in the reply body, and the driver performs file writing and
evaluation. In the local collection, the model proposes a \texttt{write}
or \texttt{edit} operation whose arguments contain the code. The
generated stream retains those argument tokens and their probabilities,
while the tool-event record retains the proposed operation and its
execution status.

Reply-body collection enabled the main experiments through the tested
DeepSeek API. The local records demonstrate probability capture through
the agent's file-writing interface, including exact matches between
recovered code strings and tool inputs. Together, these results provide
practical collection paths for studying code generation both within
replies and within tool operations.

\hypertarget{limitations}{%
\subsection{6. Limitations}\label{limitations}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Model state.} The main measurements describe an aligned model
  at inference. A matched measurement of the base policy before
  fine-tuning would clarify how the observed distribution relates to the
  rollout distribution discussed by CUDA Agent
  \citep{cudaagent, surrogate}.
\item
  \textbf{Model coverage.} Families A and B use one API model. The
  Qwen3-4B-AWQ records extend the collection interface to local tool
  calls and are reported as a separate supplement.
\item
  \textbf{Task coverage.} The selected operator chains combine a heavy
  operation with subsequent passes. Their implementation arrangements
  cover a limited part of the kernel-design space. More demanding
  choices involving shared-memory intermediates, access-pattern
  transformations, split-K reductions or online softmax would extend
  this coverage.
\item
  \textbf{Context composition.} Failure-following responses account for
  87.5\% of Family B's tokens. The reported regional distributions
  therefore weight unsuccessful revision heavily, and the driver defect
  contributes to that mixture.
\item
  \textbf{Statistical dependence.} Tokens within a completion are
  dependent. The nominal Fisher-test significance values use token-level
  counts; a run-level analysis would provide a complementary estimate of
  uncertainty.
\item
  \textbf{Training measurements.} The experiment records inference-time
  probabilities. Testing their relationship to importance-ratio
  instability requires collecting probabilities and training diagnostics
  within the same rollout and update process.
\item
  \textbf{Collection interface.} The main regional comparisons use
  reply-body code. The supplementary local audit documents
  code-probability capture inside tool arguments, providing a second
  interface for future comparisons.
\item
  \textbf{Region assignment.} Fence-based assignment includes comments,
  tracebacks and shell commands in the code region when they appear
  inside fences. The analysis quantifies the contribution of comments;
  finer annotation would separate the remaining forms of fenced content.
\item
  \textbf{Rewriting context.} A failed evaluation can change both the
  feedback content and the amount of new implementation the model must
  generate. Requesting a complete rewrite after success would help
  distinguish these contributions to the response distribution.
\end{enumerate}

\hypertarget{conclusion}{%
\subsection{7. Conclusion}\label{conclusion}}

The measured probability cost is concentrated in the prose surrounding
generated kernels, while CUDA/Triton vocabulary and code continuations
have relatively low threshold rates. This pattern appears in collections
containing 98,533 tokens on elementwise or reduction tasks and 542,611
tokens on operator chains. Contextual inspection locates much of the
tail in comments, identifier choices, punctuation and malformed output.

Within the operator-chain collection, removing comments gives a
code-side threshold rate of 0.33\%, compared with 13.56\% for prose. The
lowest-probability 5\% of code contributes 98.1\% of its total cost,
showing how sparse that tail is. The minimum code-token probability
remains approximately four hundred times the quoted floor. These
observations challenge the vocabulary-based attribution of the
probability cost and direct attention to the text and contexts produced
during kernel development.

The local audit additionally recovers probabilities for 3,162 tokens
inside 40 code-bearing tool arguments. It establishes a collection route
through file-writing tools alongside the reply-body method used in the
main experiment. Together, the measurements and collection methods
support further study of how implementation, explanation and evaluation
feedback contribute to the probability distribution encountered by a
kernel-writing agent.
