# AGENTS.md — `flashrt/apps/`

Each subdirectory of `flashrt/apps/` is one application:

```
flashrt/apps/<app>/
├── README.md          ← how to run the app end-to-end (user-maintained)
├── config.yaml        ← the app runtime config: model paths, generation
│                        settings, and the shared-memory buffer names.
│                        One file, read by every backend and the frontend.
├── adapter.py         ← the frontend ↔ backend IPC contract
├── reference/         ← the user's sequential single-GPU reference backend
├── frontend/          ← the user's frontend
└── backend/           ← the coding agent's workspace: IR conversion plus
                         optimized deployment variants
```

`flashrt/apps/_template/` is the seed a user copies to start a new app;
its `backend/` subtree is the seed for a fresh agent workspace.

## Ownership: read-only vs. yours

Everything in an app directory **except `backend/`** belongs to the user
and is read-only for coding agents:

- **`reference/`** — the user's reference backend: the sequential
  pipeline, the worker, and the backend launch script. It is the
  correctness oracle for the app and the input to your IR conversion
  (Phase 1 of the repo-root `AGENTS.md` workflow). Read it carefully; do
  not edit it. If you find yourself wanting to change something here,
  that is a signal the change belongs in `backend/` instead.
- **`adapter.py`** — the IPC contract the frontend and every backend
  share. You are explicitly encouraged to import it in your own test and
  benchmark harnesses (it is the canonical way to drive a running
  backend from Python), but do not edit it.
- **`frontend/`** — the user's frontend plus its launch helpers and
  credential utilities. Do not edit it, and do not run it as part of
  your iteration loop — your loop is headless and drives the backend
  through the adapter. Do read it, so you know exactly what the
  frontend expects from a backend (cadences, lifecycle, error
  handling); at the end of the session the user will drive *your*
  backend with this unchanged frontend.
- **`config.yaml`**, **`README.md`** — the app runtime config and the
  app documentation. Read-only.

Everything below is about **`backend/`** — your workspace. All code,
configs, launch scripts, tests, benchmarks, and notes you produce live
there. Do not modify anything outside `flashrt/apps/<app>/backend/`; the
agent runs autonomously, so when you would otherwise want to change a
read-only file, vendor it into your workspace per the repo-root
`AGENTS.md` Phase-4 rule "Read-only areas are not a blocker — vendor the
file into your workspace", or re-implement against shared primitives in
your workspace per the "Multi-GPU coordination" rule.

The `backend/` directory ships pre-seeded when the user copies
`flashrt/apps/_template/`. If it is missing for your app, create it by
copying the seed:

```bash
cp -r flashrt/apps/_template/backend flashrt/apps/<app>/backend
```

The seed is an empty, non-app-specific skeleton (directory layout plus a
README stub plus an experiment-log stub). Do not edit the template
itself; copy and fill in the copy.

## Expected sub-layout for `flashrt/apps/<app>/backend/<platform>/`

Your variants are platform-partitioned: everything below lives under
`flashrt/apps/<app>/backend/<platform>/`, where `<platform>` is `cuda`
or `rocm` matching the platform you target. The shared
`backend/launch.py` dispatcher (one level up, not yours to edit) selects
the current platform's set at runtime. Resolve repo-root or app-directory
paths via `flashrt.paths.repo_root()` / `app_dir(<app>)`, never by counting
`..` from `__file__`.

The seed from `_template/` provides a `platform_name/` skeleton with the
top-level folders. Rename it to your target platform (`cuda` or `rocm`),
then grow the subtree as you work through the phases. The layout below is
a convention, not a hard schema, but following it keeps later iterations
(and the user) able to navigate what you produced.

```
flashrt/apps/<app>/backend/<platform>/
├── README.md              ← you maintain this; it documents the
│                            currently-recommended variant and how to
│                            launch it end-to-end against the unchanged
│                            frontend under flashrt/apps/<app>/frontend/.
├── __init__.py
│
├── ir/                    ← Phase 1–2: your IR conversion
│   ├── __init__.py
│   ├── graph_builder.py   ← builds IRGraph instances representing the
│   │                        full exposed computation graph: the worker
│   │                        (high-level stage scheduling) and one or
│   │                        more model-level graphs (fine-grained ops
│   │                        within each exposed model); registers the
│   │                        operator instances defined in ops.py
│   ├── ops.py             ← operator definitions: IROperator
│   │                        subclasses and/or @ir_operator-decorated
│   │                        functions, wrapping the reference's model
│   │                        runners and external engines. Each op
│   │                        attaches its own execute(inputs, ctx, state)
│   │                        — there is no separate dict of impls
│   └── ...                ← any helpers the IR conversion needs
│
├── <variant_name>/        ← Phase 3–4: one subpackage per deployment
│   ├── __init__.py
│   ├── worker.py          ← your worker + any model pipeline(s),
│   │                        matching the adapter contract at
│   │                        flashrt/apps/<app>/adapter.py
│   ├── config.py          ← (optional) typed config façade
│   └── ...                ← whatever helpers the variant needs
│
├── configs/
│   └── <variant_name>.yaml
├── examples/
│   └── launch_<variant_name>.py
├── tests/
│   ├── common.py          ← shared harness utilities
│   ├── fixtures/          ← small simulated-input fixtures
│   ├── test_ir.py         ← Phase 2: IR validation harness (compares
│   │                        executor output against reference)
│   └── test_<variant>.py  ← Phase 4: deployment correctness harness
├── benchmarks/
│   ├── common.py          ← measurement utilities for every active
│   │                        optimization target (latency-to-first-
│   │                        output, sustainable-output-rate sweep,
│   │                        per-app override, etc.)
│   ├── bench_<variant>.py
│   └── results/
│       └── <variant>_<hardware>_<date>.json
└── notes/
    ├── experiment_log.md  ← seeded from the template
    └── design_<topic>.md
```

### No stub variants — measure it or remove it

A variant subdirectory under `flashrt/apps/<app>/backend/` must either:

- contain a runnable worker that was actually launched end-to-end
  **and** have a matching benchmark JSON at
  `flashrt/apps/<app>/backend/benchmarks/results/<variant>_*.json` plus a
  recorded correctness verdict in the experiment log, or
- not exist at all.

No stubs. No scaffolded-but-unimplemented subpackages. No
`raise NotImplementedError` constructors checked in as a "placeholder
for the next variant". No experiment-log entries of the form
`Verdict: needs-followup` attached to a variant that was never
measured; `needs-followup` is reserved for variants that were run,
produced a measured result, and need more work to interpret that
result — not for variants that were never run at all. Measure the
variant or remove it; unmeasured shelved work is indistinguishable
from a false claim of progress.

Variants may vendor copies of read-only files from outside
`flashrt/apps/<app>/backend/` into their own subdirectory and modify the
copies (see "Read-only areas are not a blocker — vendor the file
into your workspace" in the repo-root `AGENTS.md`). A vendored file
is not a stub — it is a legitimate part of the variant's code — as
long as the variant as a whole reaches a terminal status.

### The `ir/` subdirectory

This is where your IR conversion lives (Phases 1–2 of the workflow
described in the repo-root `AGENTS.md`). It is the bridge between
the user's reference backend and your deployment variants.

**`graph_builder.py`** constructs `IRGraph` instances that represent
the full exposed computation graph, using the data structures from
`flashrt.ir.graph`. You will typically build:
- A worker-level graph representing the high-level stage scheduling
  (which stages run, what data flows between them, which are
  streaming). This covers the worker and any black-box stages.
- One or more model-level graphs, one per exposed model in the
  pipeline. Each model-level graph represents the fine-grained
  operators within that model (e.g., individual denoising steps,
  VAE decode). A pipeline with multiple exposed models gets
  multiple model-level graphs.

Inside the builder, register `StateObject`s for every piece of
persistent state your operators will touch, instantiate the op
classes / decorator-bound op objects defined in `ops.py` (`g.add_operator(DiTDenoiseStep(k, ...))`,
`g.add_operator(text_encoder_prefill)`, etc.), wire edges between
their ports, and list each operator in either `preamble_ops` (runs
once at session init) or `chunk_ops` (runs once per chunk).

**`ops.py`** defines the operators themselves. Each operator carries
its own implementation — there is no separate "callable dict" passed
to the executor. Two patterns, both living in this file:

- **Subclass `IROperator`** for parameterized operators where the
  same kind of op is instantiated many times with different
  arguments (e.g., one class `DiTDenoiseStep` instantiated once per
  inference step, each with its own KV cache). Override
  `execute(inputs, ctx, state)` and, if needed, `should_run(ctx)`.
- **Apply `@ir_operator(...)`** from `flashrt.ir` to a function with
  signature `(inputs, ctx, state) -> dict` for one-off leaf ops
  (text encoder prefill, VAE decode, Wav2Vec2 feature extraction).
  The decorated name is an `IROperator` instance ready to pass
  straight to `g.add_operator(...)`.

Operators access persistent state through the `state` argument of
`execute`: `state.get(name)` returns the stored object (including
for in-place mutation, e.g., a runner writing through a KV cache
object), and `state.set(name, value)` rebinds the stored value for
genuine reassignment. Both reject any `name` not in the op's
declared `state_reads` / `state_writes`, which catches
declaration/implementation drift at the earliest point.

The `context` object is yours to define — it carries per-chunk
scalars, model runner handles, timesteps, and any other session-wide
helpers the operators need. It is not inspected by the executor.

**Phase 2 validation skeleton** (for `tests/test_ir.py`):

```python
from flashrt.ir import SequentialExecutor
from flashrt.apps.<app>.backend.ir.graph_builder import build_model_graph

graph = build_model_graph(cfg)
executor = SequentialExecutor(graph)
# Pre-populate state that exists before any op runs (e.g., externally
# allocated empty KV caches). Preamble ops can also populate state
# via state.set(...) during executor.run_preamble(...).
executor.init_state({f"step_{k}_kv": allocate_cache(cfg)
                     for k in range(cfg.num_inference_steps)})

executor.run_preamble(preamble_inputs, ctx)
for chunk_idx in range(num_chunks):
    ctx.chunk_idx = chunk_idx
    out = executor.run_chunk(chunk_inputs[chunk_idx], ctx)
    # compare `out` against reference backend output for this chunk
```

### Variant naming

Name variants after the *idea*, not the order in which you tried them.
You will reread the experiment log later and names like `v1`, `v2`,
`try3` will be useless.

### Backend contract

Every variant must:

- Honor the same frontend-facing contract as the user's reference
  backend for this app: create the same IPC / shared-memory handles,
  respond to the same control protocol, and produce outputs with the
  same shapes, dtypes, and cadence. The authoritative definition of
  that contract is the shared adapter under
  `flashrt/apps/<app>/adapter.py` plus the user's reference backend under
  `flashrt/apps/<app>/reference/` — read them side-by-side. Additionally,
  `flashrt/apps/<app>/frontend/` shows exactly how the adapter is driven
  in practice; read it for context but do not execute it as part of
  your loop.
- Be launchable standalone, from the repo root, via a script under
  `flashrt/apps/<app>/backend/examples/`. The user will ultimately launch
  your backend and drive it with the unchanged frontend under
  `flashrt/apps/<app>/frontend/`, so your launch surface has to make that
  possible.
- Pass your correctness harness in `flashrt/apps/<app>/backend/tests/`.

### Correctness harness pattern

You write **two** correctness harnesses per app:

- A **Phase 2 IR validation harness** (typically `tests/test_ir.py`)
  that runs the `SequentialExecutor` over your IR graph and compares
  its outputs against the reference backend driven through the
  adapter. This validates that your IR conversion faithfully captures
  the reference's behavior.
- A **Phase 4 deployment correctness harness** (typically
  `tests/test_<variant>.py`) that launches your candidate backend as
  a subprocess and compares its outputs against the reference backend
  driven through the same adapter. This validates each deployment
  variant.

Both follow the same subprocess-driven pattern and the same hard rule:
**a harness that has not actually run end-to-end and printed a
verdict is not a verification; static inspection of the code under
test does not substitute for executing it.**

You do not use the user's frontend as your harness. Drive the backend
directly through the shared adapter instead:

1. Load a small simulated-input fixture from `tests/fixtures/`. Keep
   fixtures small — a few seconds of content, at most.
2. Launch the user's reference backend as a subprocess, with its own
   set of IPC handle names. **Wrap the entire interaction in a
   `try / finally` block** that guarantees the subprocess is
   terminated and waited on — see "Process cleanup" below.
3. Drive the reference backend via the shared adapter class (imported
   from `flashrt.apps.<app>.adapter`), collect every output, and cleanly
   terminate it (adapter terminate signal → `proc.terminate()` →
   `proc.wait(timeout=...)` → `proc.kill()` if needed).
4. Launch your candidate backend as a subprocess with a disjoint set
   of IPC handle names. Same `try / finally` cleanup rule.
5. Drive the candidate backend with the same fixture, collect every
   output, and cleanly terminate it.
6. Compare output sequences element-wise / chunk-wise with explicit
   tolerances. Document each tolerance in-comment with its
   justification (floating-point non-associativity, reduced-precision
   accumulation, CUDA graph replay noise, etc.). **A tolerance of
   "whatever passes today" is not acceptable — pick a number, justify
   it, and hold yourself to it.**
7. Print a clear **PASS** or **FAIL** verdict to stdout. If the
   harness script exits without printing a verdict, the run is
   invalid.
8. After both backends are terminated, verify with a `ps` check (or
   `pgrep`) that no orphaned backend processes remain. If any do,
   kill them and treat the run as suspect.

### Benchmark harness pattern

Use the same subprocess-driven adapter pattern but measure
timestamps and steady-state behavior instead of comparing outputs.
The same `try / finally` cleanup rules apply — the backend must be
cleanly terminated after every benchmark run, and orphan processes
must be checked for.

The harness must produce numbers for every target the session is
ranked against. Under the defaults defined in the repo-root
`AGENTS.md` "Default optimization targets" section, that means
**both** of:

- **Latency to first output.** Mark `t_in` at the moment the final
  chunk of a simulated input is pushed to the adapter; mark
  `t_first_out` at the first corresponding output chunk returned
  from the adapter. Repeat over N ≥ 5 inputs, report median and
  p95 of `t_first_out - t_in`.
- **Maximum sustainable output rate (with smoothness).** For a
  pipeline that produces more than one output chunk per input,
  drive the adapter with a steady offered input rate and find the
  highest rate at which the output rate matches it indefinitely
  (the consumer never stalls and the backend's input queue does
  not grow without bound). Report the rate in the app's natural
  output unit (chunks/s, frames/s, tokens/s). Alongside the rate,
  record the **inter-chunk-gap distribution** (median, p95, and
  the fraction of gaps exceeding the app's natural per-chunk
  budget) as the smoothness side condition. For a pipeline where
  one input produces exactly one output chunk, this number
  collapses to `1 / (t_first_out - t_in)` and you do not need to
  report it as a separate column.

When the user has named a per-app override (system throughput,
cost per request, a specific tail-latency percentile, memory
footprint at fixed latency, etc.), the harness must additionally
produce numbers for the user's named target and treat it as the
primary axis the variant queue is ranked against; the defaults
above stay in the JSON as secondary evidence per the "Per-app
overrides" rule.

Other harness invariants:

- Print the actual numbers to stdout. If the harness exits
  without printing numbers, the run is invalid — do not record
  results.
- **Cleanly terminate the backend** after the measurement is
  done. Verify with `ps` / `pgrep` that no orphaned processes
  remain.
- Persist each run as a JSON (or similar structured) file under
  `benchmarks/results/`, with enough metadata (git diff summary,
  `CUDA_VISIBLE_DEVICES`, hardware, attention backend, the active
  target set, etc.) that a future iteration can diff runs without
  rerunning them.

### Process cleanup (critical)

**Every** test or benchmark script you write must guarantee that all
backend subprocesses it spawned are dead before the script exits. This
is non-negotiable. Leaked processes corrupt subsequent runs, waste GPU
memory, and — most importantly — mean the harness did not actually
complete, which invalidates any results you recorded.

Pattern:

```python
import os, signal, subprocess

proc = subprocess.Popen(
    [...],
    preexec_fn=os.setsid,  # new process group so we can kill children
)
try:
    # ... drive the backend through the adapter ...
finally:
    # 1. Ask nicely
    proc.terminate()
    try:
        proc.wait(timeout=15)
    except subprocess.TimeoutExpired:
        # 2. Kill the whole process group
        os.killpg(os.getpgid(proc.pid), signal.SIGKILL)
        proc.wait()
    # 3. Clean up IPC handles
    # (remove /dev/shm/<prefix>* files)
```

After every harness run (success or failure), execute a quick orphan
check:

```bash
pgrep -f 'flashrt/apps/<app>/backend' || echo "no orphans"
```

If orphans exist, kill them before proceeding. If a harness
consistently leaks processes, fix the harness before recording any
results from it.

### Other process hygiene

- Before launching a backend subprocess, clean up stale IPC handles
  from prior crashed runs (`ipcs -m`, stale files under `/dev/shm`).
  Prefer random handle-name prefixes per run so you do not collide
  with yourself.
- Pin `CUDA_VISIBLE_DEVICES` explicitly for each launched process;
  do not rely on the ambient environment. This makes co-location
  experiments reproducible.
- Always run inside the pre-configured environment resolved at
  session start (the `flashrt` conda env by default, or whatever the
  user specified, or the answer to the start-of-session question if
  neither applied). Activate it (`conda activate <name>` or
  `source <venv-path>/bin/activate`) at the top of shell scripts, or
  invoke its interpreter directly (`<env-path>/bin/python …`). See
  the repo-root `AGENTS.md` "Environment" section for the full
  resolution rule and rationale.
- Keep per-variant logs alongside the JSON results under
  `benchmarks/results/` so a regression is diagnosable without a
  rerun.

### Experiment log format

Append one block per milestone to
`flashrt/apps/<app>/backend/notes/experiment_log.md`. The log has two
sections: the IR conversion record (Phases 1–2) and the deployment
iteration records (Phases 3–4).

Every entry's PASS / FAIL claim and every numerical result **must be
backed by a pointer to a live artifact on disk** — a log file, a
JSON result file, a stored hash — so that a later reader (or you, on
the next iteration) can re-open the evidence without re-running the
experiment. A log entry without those live artifacts is treated as a
*proposal*, not a *result*.

**IR conversion record** (one block, at the top of the log):

```markdown
## IR Conversion  (YYYY-MM-DD)
- Worker graph: <number> operators, <number> edges
  - Black-box stages: …
  - Exposed stages: …
  - Streaming edges: …
- Model graph(s): <graph_name>: <number> operators, <number> edges
  - State objects: …
  - Chunk-periodic operators: …
- IR validation: PASS / FAIL
  - fixture: <path to the simulated-input fixture used>
  - reference_run: <stdout/log path for the reference backend run>
  - executor_output_hash: <sha256 or diff summary of the
    SequentialExecutor's collected outputs>
  - reference_output_hash: <sha256 or diff summary of the reference
    backend's collected outputs, over the same fixture>
  - tolerance: <documented numerical tolerance and justification>
- Analysis summary:
  - Pipeline stages: <N> stages (<list of stage groupings>)
  - Streaming overlaps: …
  - Critical path: …s (<list of operators>)
  - Bottleneck stage: Stage <N> (<latency>s)
  - Key independent pairs: …
```

**Variant queue** (one block at the top of the deployment-iteration
section, updated **between every variant you measure** — see the
"Maintain a visible, evolving variant queue" rules in the repo-root
`AGENTS.md` Phase 4 section):

```markdown
## Variant Queue  (last updated YYYY-MM-DD)

| # | name | hypothesis | IR basis | predicted impact | status |
| --- | --- | --- | --- | --- | --- |
| 1 | `variant_a` | one sentence | pipelining / streaming / parallelism / co-location / … | which active optimization target, rough magnitude | planned / in_progress / measured / blocked / discarded |
| 2 | `variant_b` | … | … | … | … |
| … | … | … | … | … | … |

Rationale for ordering: <brief note on why the queue is ordered this
way; should reference IR-analysis-ranked expected impact, not
implementation cost>

Changelog:
- YYYY-MM-DD: initial queue committed from IR analysis.
- YYYY-MM-DD: measured `variant_a` → <result summary>; added
  `variant_c` as a follow-up because …; re-ordered X above Y
  because …
- YYYY-MM-DD: `variant_d` removed as `discarded` because the IR
  originally marked `state_X` independent of `state_Y` across
  chunks, but reviewing `ir/ops.py` shows they actually share the
  underlying ring buffer; the transformation is not legal. IR
  fix: <path to ir/ fix>. See the adversarial-self-framing
  paragraph on the `variant_d` log block.
- …
```

The queue is an evolutionary-search artifact, not a static plan:
every measured variant must add its row update + any follow-up
ideas + any re-ordering to the changelog. Queue entries may only
be `discarded` under the single acceptable removal reason in the
repo-root `AGENTS.md` (the IR analysis was wrong about the
transformation's legality); "too much implementation work" is not
an allowed reason, and neither is "a different measured variant
looks like it dominates this one."

**Deployment iteration records** (one block per variant, appended
below the variant queue):

```markdown
## <variant_name>  (YYYY-MM-DD)
- Hypothesis: …
- IR analysis basis: <cite specific pipeline stage, streaming overlap,
  independent-pair result, or sub-IR-granularity opportunity that
  makes this legal; if the change attacks something not directly
  surfaced by the IR analysis tools, say so explicitly>
- Optimization target(s) attacked: <one or more of the active
  targets for this session — under defaults, "latency-to-first-
  output", "sustainable-output-rate", or "both"; under a per-app
  override, name the user's target plus any defaults the variant
  also moves>
- Change relative to previous baseline: …
- Hardware: GPUs=…, attention_backend=…, other knobs=…
- Correctness: PASS / FAIL (tolerance=…, diff summary=…)
  - correctness_log: <path to the correctness harness's stdout/log
    for this run — required>
- t_first_out − t_in: median=…ms, p95=…ms
- Sustainable output rate: …<unit>/s  (omit if the pipeline emits
  exactly one output chunk per input; otherwise include the inter-
  chunk-gap median, p95, and over-budget fraction as the smoothness
  side condition)
- <user-named override target, if any>: …
- benchmark_json: <path under benchmarks/results/ containing the raw
  per-run timings, the steady-rate sweep, and metadata — required>
- Δ vs. previous baseline: <one entry per active target, named
  explicitly>: …
- Verdict: promote / discard / needs-followup
- Follow-ups: <new variant ideas this result surfaced. Every
  follow-up named here must appear as a `planned` row in the
  Variant Queue above inside the same edit that finalises this
  entry, or be explicitly removed per the repo-root `AGENTS.md`
  acceptable-reasons list. See the "Follow-ups must be enqueued,
  not narrated" rule in the repo-root `AGENTS.md` Phase 4. Free-text
  "deferred", "noted for later", "scoped but not built", or "a
  follow-on session can pick this up" is not permitted>
```

For variants with `blocked` or `discarded` status, the log block
additionally **must** include an adversarial-self-framing paragraph
immediately after the status line, in the form specified under
"Adversarial self-framing (required)" in the repo-root `AGENTS.md`
Phase 4. The paragraph's "concrete evidence" pointer must be a
specific on-disk path — an artifact file, a failing-test file, or
(for discarded entries) the specific IR-file fix that demonstrates
reason (a). Prose justifications do not satisfy this requirement.

If your variant improves one active optimization target but
regresses another (under defaults: improves latency-to-first-
output but regresses sustainable-output-rate or its smoothness
side condition, or vice versa; under a per-app override: improves
the user's named target but regresses one of the defaults retained
as a secondary constraint, or vice versa), the verdict cannot be
`promote` — record the trade-off and keep the variant's row as
needs-followup, then enqueue a combined / adjusted variant that
targets the regressed axis.

The log, the README, and any final status message must be free of
the forbidden session-handoff phrases enumerated in the repo-root
`AGENTS.md` section "Forbidden session-handoff language". Before
handoff, run a mechanical text search for each forbidden phrase
and fix any match.

Append, never rewrite. The log is the reason you will not re-run a
failed experiment twice. Any entry whose `correctness_log` or
`benchmark_json` pointer references a file that does not actually
exist on disk is invalid — treat the variant as unmeasured and run
it.

### Importing from the shared runtime, IR, and adapters

Import as much as you can from the shared `flashrt/*` runtime
(see the "Resources you can use" section in the repo-root `AGENTS.md`),
from `flashrt.ir` for the IR framework, and from
`flashrt/apps/<app>/adapter.py` for the adapter class that drives your
test / benchmark harnesses. You do not need to import from
`flashrt/apps/<app>/reference/` at all — everything you need at runtime is in
the shared runtime, the IR framework, and the shared adapter. The
default is to *use* the shared abstractions, not vendor or
re-implement them: gratuitous copies of shared-runtime / IR / adapter
code into your variant create drift and silent inconsistencies. When
the shared runtime genuinely does not cover behavior you need, the
agent runs autonomously — there is no "stop and ask" escape valve —
and the path forward is one of:

- Vendor the offending shared file into the variant's directory and
  modify the copy, per the repo-root `AGENTS.md` Phase-4 rule
  "Read-only areas are not a blocker — vendor the file into your
  workspace".
- Re-implement against shared primitives, subject to the four
  constraints in the repo-root `AGENTS.md` "Multi-GPU coordination"
  rule (use sparingly, build on the shared substrate, preserve the
  implicit and explicit globals the rest of the codebase relies on,
  and vendor the new code under `flashrt/apps/<app>/backend/`).

Both paths require the on-disk audit / justification the linked
rules spell out. Neither requires user consultation.

### Keep variants self-contained

Copy shared helpers between variants if you need to diverge. Your
variants should be able to evolve independently from one another and
from the reference implementation, so resist the urge to introduce a
`flashrt/apps/<app>/backend/common/` grab bag until a pattern has clearly
stabilized.
