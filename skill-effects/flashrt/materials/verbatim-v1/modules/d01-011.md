**a harness that has not actually run end-to-end and printed a
verdict is not a verification; static inspection of the code under
test does not substitute for executing it.**

You do not use the user's frontend as your harness. Drive the backend
directly through the shared adapter instead:

1. Load a small simulated-input fixture from `tests/fixtures/`. Keep
   fixtures small — a few seconds of content, at most.
2. Launch the user's reference backend as a subprocess, with its own
   set of IPC handle names. **Wrap the entire interaction in a
   `try / finally` block** that guarantees the subprocess is
   terminated and waited on — see "Process cleanup" below.
3. Drive the reference backend via the shared adapter class (imported
   from `flashrt.apps.<app>.adapter`), collect every output, and cleanly
   terminate it (adapter terminate signal → `proc.terminate()` →
   `proc.wait(timeout=...)` → `proc.kill()` if needed).
4. Launch your candidate backend as a subprocess with a disjoint set
   of IPC handle names. Same `try / finally` cleanup rule.
5. Drive the candidate backend with the same fixture, collect every
   output, and cleanly terminate it.
6. Compare output sequences element-wise / chunk-wise with explicit
   tolerances. Document each tolerance in-comment with its
   justification (floating-point non-associativity, reduced-precision
   accumulation, CUDA graph replay noise, etc.). **A tolerance of
   "whatever passes today" is not acceptable — pick a number, justify
   it, and hold yourself to it.**
7. Print a clear **PASS** or **FAIL** verdict to stdout. If the
   harness script exits without printing a verdict, the run is
   invalid.
8. After both backends are terminated, verify with a `ps` check (or
   `pgrep`) that no orphaned backend processes remain. If any do,
   kill them and treat the run as suspect.
