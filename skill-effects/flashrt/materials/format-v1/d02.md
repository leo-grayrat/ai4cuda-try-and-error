# AGENTS.md — `flashrt/ir/`

**This directory is read-only for coding agents.**

The IR (Intermediate Representation) framework provides data structures and tools for representing computation graphs as explicit, analyzable, *executable* objects. You import from this module freely but do not edit any files in it.

## What each file does

- **`graph.py`** — Core data structures you use to build IR graphs:
  - `IRGraph`: the top-level graph container (operators, edges,
    state objects, external I/O, preamble/chunk phases).
  - `IROperator`: a computation node **with an attached
    implementation**. Subclass it and override
    `execute(inputs, context, state) -> dict` (and optionally
    `should_run(context) -> bool`). The base constructor takes
    keyword-only metadata: `name`, `op_type`, `inputs`, `outputs`,
    `state_reads`, `state_writes`, `stream_mode`, `sub_graph`,
    `config`. A plain `IROperator(...)` call (without subclassing
    or overriding `execute`) produces a structural-only op whose
    default `execute` raises `NotImplementedError` — useful for
    scaffolding, not for running.
  - `IREdge`: a dependency between operators. Data edges carry
    tensors between ports. Ordering edges enforce execution order
    without data transfer (set both ports to `None`).
  - `StateObject`: a named persistent state (e.g., a KV cache).
    Its `scope` controls cross-chunk dependency analysis:
    `"chunk_persistent"` creates cross-chunk constraints,
    `"session_init"` and `"ephemeral"` do not.
  - `StateStore`: the `Protocol` an operator's `execute` receives
    as its third argument. Exposes `get(name) -> Any` and
    `set(name, value) -> None`. Both raise if `name` is not in
    the operator's declared `state_reads` / `state_writes`; this
    is the runtime check that keeps declared state dependencies
    honest (see "State access" below).
  - `TensorPort`: a named input/output slot with optional shape and
    dtype hints.
  - `OpType`: `BLACK_BOX` (opaque), `EXPOSED` (visible internals),
    `COMPOSITE` (contains sub-graph).
  - `StreamMode`: `BATCH` or `STREAMING`.
  - `StreamingInfo` / `StreamingPattern`: metadata attached to
    streaming edges.

- **`ops_base.py`** — `@ir_operator(...)` decorator. Wraps a
  function `fn(inputs, context, state) -> dict` into an
  `IROperator` subclass instance with all metadata baked in, so
  you can pass the decorated object straight to
  `graph.add_operator(...)`. Use this for one-off leaf ops; prefer
  subclassing `IROperator` directly when you need one class
  instantiated with many different parameters (e.g., one
  `DiTDenoiseStep` class, one instance per denoising step). The
  decorator also accepts an optional `should_run=lambda ctx: ...`
  for chunk-conditional ops.

- **`executor.py`** — `SequentialExecutor(graph)` that runs an
  `IRGraph` on a single device in topological order. Use this to
  validate your IR conversion in Phase 2. It takes only the graph;
  operator implementations live on the operators themselves. Key
  surface:
  - `init_state({name: value, ...})` — pre-populate persistent
    state before any operators run (e.g., empty KV caches
    allocated at session start). Preamble operators can also
    populate state by calling `state.set(name, value)` during
    `run_preamble`.
  - `run_preamble(external_inputs, context)` — runs the
    `preamble_ops` once per session.
  - `run_chunk(external_inputs, context)` — runs the `chunk_ops`
    once per chunk. Call it in a loop over chunks.
  - `context` is opaque — define it however your operators need.
    It is the right place for per-chunk scalars, model runner
    handles, and other session-wide helpers.
  - `state` is managed by the executor (in a dict it owns) and
    handed to each op through a scoped `StateStore` that rejects
    any access to names the op didn't declare.

- **`analysis.py`** — Tools the agent runs on validated IR graphs
  to discover optimization opportunities:
  - `analyze_cross_chunk_dependencies(graph)`: finds operators
    that share `chunk_persistent` state → cross-chunk constraints.
    Returns independent pairs → pipeline parallelism candidates.
  - `find_pipeline_stages(graph)`: partitions operators into
    stages by grouping shared-state operators. Each stage = one
    GPU.
  - `find_streaming_overlaps(graph)`: finds streaming edges with
    rate-conversion metadata.
  - `compute_critical_path(graph, latencies)`: longest dependency
    chain through one chunk.
  - `summarize_graph(graph, latencies)`: all of the above in a
    human-readable summary. **Start here.**

## Building an operator

**Parameterized ops — subclass `IROperator`.** Use this when the
same kind of operator is instantiated many times with different arguments (e.g., one denoising step per inference step, each with its own KV cache):

```python
from flashrt.ir import IROperator, OpType, TensorPort

class DiTDenoiseStep(IROperator):
    def __init__(self, step_idx: int, dit_runner):
        cache = f"step_{step_idx}_kv"
        super().__init__(
            name=f"dit_denoise_{step_idx}",
            op_type=OpType.EXPOSED,
            inputs=[TensorPort("latents"), TensorPort("timestep")],
            outputs=[TensorPort("noise_pred")],
            state_reads=[cache],
            state_writes=[cache],  # declares in-place mutation
        )
        self.cache = cache
        self.dit_runner = dit_runner

    def execute(self, inputs, ctx, state):
        kv = state.get(self.cache)          # ref to the cache object
        self.dit_runner.kv_memory = kv       # runner mutates it in place
        noise_pred = self.dit_runner.run(
            latents=inputs["latents"],
            timestep=inputs["timestep"],
            ...,
        )
        return {"noise_pred": noise_pred}
```

**Leaf ops — use `@ir_operator`.** For one-off operators with no
per-instance parameterization:

```python
from flashrt.ir import OpType, TensorPort, ir_operator

@ir_operator(
    name="text_encoder_prefill",
    op_type=OpType.EXPOSED,
    inputs=[TensorPort("prompt")],
    outputs=[TensorPort("embeds")],
    state_writes=["prompt_embeds"],
)
def text_encoder_prefill(inputs, ctx, state):
    embeds = ctx.text_encoder.encode(inputs["prompt"])
    state.set("prompt_embeds", embeds)
    return {"embeds": embeds}
```

The decorated name binds to an `IROperator` instance (not a
function); register it with `graph.add_operator(text_encoder_prefill)`.

**Chunk-conditional ops.** If an op should only run under some
condition (e.g., only on chunk 0), override `should_run(ctx)` on
the subclass, or pass `should_run=lambda ctx: ...` to the
decorator. The executor skips the op when `should_run` returns
False; downstream ops that depend on its outputs must tolerate the
value being absent (typically via their own `should_run`).

## State access

State lives in a dict owned by the `SequentialExecutor`. Each op
receives a `StateStore` scoped to its own declared dependencies:

- `state.get(name)` — returns the stored object. Requires `name`
  in the op's `state_reads ∪ state_writes`.
- `state.set(name, value)` — rebinds the stored object for
  `name`. Requires `name` in the op's `state_writes`.

In-place mutation (a DiT runner writing through a KV cache object)
is expressed by declaring `state_writes=[name]` and calling only
`state.get(name)` — the returned object is the real stored object,
and mutations to it persist. No `state.set` is needed for in-place
writes. Runtime enforcement catches accesses to names the op did not declare; it does *not* try to catch an op that declared
`state_reads=[name]` but mutated the returned object anyway
(Python can't cheaply freeze tensor state). The declaration is the contract the analysis tools trust, so keep your declarations honest.

Pre-populate state that exists before any op runs (typically externally-allocated KV caches, ref tensors, cached motion latents)
by calling `executor.init_state({name: value, ...})` after
constructing the executor and before `run_preamble` / `run_chunk`.

## How to use this module

See the repo-root `AGENTS.md` section "The IR workflow" for the
full workflow. In brief:

1. **Phase 1**: Define your operators (subclasses or
   `@ir_operator`) in `flashrt/apps/<app>/backend/ir/ops.py`, then build
   `IRGraph` instances in `flashrt/apps/<app>/backend/ir/graph_builder.py`
   by inspecting the full exposed computation graph in the user's
   reference backend under `flashrt/apps/<app>/reference/` (the worker, any
   model pipeline(s), and their interactions).
2. **Phase 2**: Construct `SequentialExecutor(graph)`, pre-populate
   any externally-allocated state with `executor.init_state(...)`,
   run it with test inputs, and compare against the reference
   backend's output.
3. **Phase 2 continued**: Run `summarize_graph()` on the validated
   graph to discover pipeline stages, streaming overlaps, and
   independent operator pairs.
4. **Phase 3**: Use the analysis results to design deployment
   variants.

If you believe the IR framework is missing a capability you need,
work around it inside `flashrt/apps/<app>/backend/`. The agent runs
autonomously — there is no "ask the user" escape valve — and the shape of the workaround is whichever of the two paths in the repo-
root `AGENTS.md` applies: vendor the offending IR file per "Read-
only areas are not a blocker — vendor the file into your workspace", or re-implement against the existing IR primitives subject to the constraints in the "Multi-GPU coordination" rule (build on the shared substrate, preserve the globals the rest of the codebase
relies on, vendor the new code under `flashrt/apps/<app>/backend/`).
