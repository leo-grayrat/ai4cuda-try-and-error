# 首轮模型试跑与工具校准

这是开发试跑。比较对象为同一 FlashRT 派生本机任务上的原文与 Phase 4 整理稿；尚未冻结正式样本和结论。完整记录见 [collection.json](collection.json)，压缩归档保留全部 API 请求、响应、过程事件、候选源码及独立验证证据。

## 同工具、同预算的一组记录

original-03 与 phase4-01 的运行器校验值、共同任务前缀、16 次 API 请求上限、24,000 个总生成 token 预算和单次上限一致。两者均未启用额外写入权限或提交检查器。生成量包含思考；实际均调用七次 API 后耗尽生成预算。

| 观测 | 原文 original-03 | 整理稿 phase4-01 |
| --- | ---: | ---: |
| 首次 API 输入 token | 32,488 | 27,064 |
| 累计输入 token | 290,275 | 294,569 |
| 其中缓存命中 | 238,848 | 263,552 |

| 正式提交的报告 | 无 | 无 |

整理稿这一轮写出了 `backend/worker.py`，将每次请求的整段因果网络合并计算，减少逐块的计算启动和传输。跨请求仍保留各层历史。可见验证通过后，研究方又用另一组输入独立验证通过；连续会话、末尾短块和重置均在其中。

最后一次独立负载扫描中，参考后端在测试的 50、100、200 请求/秒里，通过速率与间隔两门槛的最高档为100，候选为200。200是本次扫描的最高测试档，不是候选能力上限；窗口仅一秒。两者首块延迟中位数均约1.5ms，本轮没有显示明显首块改善。

原文这一轮没有生成文件；整理稿这一轮生成了可运行候选。两轮都没有提交报告，也未产出 IR 图、实验队列或十种方案记录。预算中止时未完成的要求逐项保留，不能把代码正确等同于完成整套说明，也不替不存在的报告评分。

## 成本应如何理解

整理稿确实减少首次输入5,424 token，但它随后进行了写入、验证和负载工具调用，累计输入反而略高。文档变短不能直接替代实际总成本测量。

缓存命中还受此前校准请求和执行顺序影响。当前表保留命中与未命中两列，没有把全部输入按未缓存价格计算，也没有用这一先后顺序比较宣称固定收费收益。正式运行需要平衡顺序并按实际用量计费。

## 试跑发现的设置问题

更早的 original-02 在单次8,192 token上限停止。当次8,192 token全部为思考，尚未调用写文件工具；累计生成11,050，总预算未耗尽。该轮与上表的不同单次上限单独分组。之后将单次上限提高至总预算，24,000的总预算不变。API 参数含义核对自 [DeepSeek 官方文档](https://api-docs.deepseek.com/api/create-chat-completion/)。

第一次准备还遇到本机默认GBK解码失败，尚未发送API请求；读取改为显式UTF-8。控制台打印中文的显示问题另经保存的API请求核对，实际传入的任务说明完好，没有替换字符。

工具初版允许读取虚拟 `evidence/` 路径，却未实现对该路径的列表操作，导致整理稿模型两次列证据目录得到空列表。这是运行器缺陷，不能据此指责模型不查证据。现已补齐虚拟目录列举。

下一版还将在工具结果中提供准确的剩余预算，并保持各条件的共同任务文字一致；启用权限或检查器时不额外增加一段条件专属提醒。提交检查器额外绑定推荐入口，防止拿另一个后端的性能记录来提交当前后端。

两条记录给出了不同产物和成本分布，样本仍只有各一次。后续先确认更充足预算下的交付、修正后的工具和机制对照，再扩大正式比较。
