# t012：长思考中有纠错，也有围绕剩余调用的筹划

此轮为 source_core、双分支任务，不含权限和检查器。已知条件下事后审阅；这里只解释该轮过程，不推断条件总体收益。完整记录在 repeat-completed-02，关键[来源哈希](repeat-review-t012.sources.json)另存。

响应8已经详细推演双分支卷积怎样合并、怎样保留跨请求历史，并考虑一次性发布全部输出的协议安全性。响应12又展开了一次很长的实现设计。它先担心 Python 实际导入的是研究方共享任务目录，自己的脚本怎样找到参考、配置与同目录模块；随后反复检查张量形状、状态更新、首块优先、整段处理、启动预热和轮询方式。这些疑虑中既有真实计算问题，也有本实验工具/目录安排引出的工作。

其中一个具体纠错有价值：最初草拟第二层输入时，它把第一层重新计算的历史前缀也拼到了第二层保存的历史后面。继续推演后它发现这样会重复历史，改为先截取当前请求对应的第一层输出，再拼第二层自己的历史。这是在写入实现前发现的状态语义错误。不能把这段思考全部算成闲聊，也不能仅凭发现过错误就断言更长思考必然值得其成本。

此轮随后实际运行了参考与候选的适配器对照，又实现图。execute-006 的输出是图分析/结构检查，不能单独作为数值验证；execute-011 才打印出两个图分别对六请求参考及CPU oracle的逐项比较，均通过。最终独立验证也通过。因此它在这些步骤上确有可运行产物。

不过，“worker_graph”和“fused_graph”实际是原始细粒度计算与融合计算两张图，不能只凭名称就确认原说明要求的高层 worker 调度与各模型层级全部表达充分。图有实际运行、图覆盖了什么、图是否先于优化，应分别判断。其实际顺序仍然是先优化并验证候选，再补图及其验证。

响应35再次花较长篇幅估算调用次数，先误把每个工具动作当作单独一次API响应，回顾工具余额后才理解可以在同一响应中提交多个动作。响应41看到开发阶段只剩一次，又把文档集中到最后一次写入。这种筹划受到实验显式倒计时的直接影响。

响应41还准确识别：50请求/秒下约19ms的长间隔多半是前一请求结束后等待下一次输入。该次工具记录的超20ms比例为4/449，约0.89%，刚好低于1%门槛；它于是认为侧条件已通过，保留更快实现，并报告发布较突发这一取舍。研究方后测同一最终代码出现5/449，约1.11%，跨过了门槛；两次的100、200档仍通过。交付前测量与后测的区别应保留，不能把报告按当时可见数据写作判成虚构。

这与 t009 构成一组可解释的过程对照：两轮都识别了输入等待空档，t009看到检查失败后重写发布策略，t012看到检查通过后保留实现。它们的文档条件也不同，不能因此隔离出单一原因；但逐次记录说明，门槛反馈与倒计时确实进入了具体决策。此轮只比较少数变体，也不能按未提供的完整Phase 4十变体下限判违规。
