# 比较方案：依据原文核对单展开

本文件是任务可行性落实前的方案草稿。来源与要求固定在 [核对单](REQUIREMENTS.zh.md)及其[可读取索引](materials/requirements-v1.json)。旧 CUDAAgent 方案不决定本研究条件数、样本数或题目。

更新：按用户纠正，任务采用本机可运行的简单单卡流程，见[选择与实测](LOCAL_TASKS.zh.md)。五个原大型应用不是试验前提。原说明本来允许用户新增应用；单卡适用性由共同任务明确，不在各条件中暗改。

## 共同基础

每次提供同一用户参考后端、适配器、输入与硬件，沿原流程完成图转换验证和部署探索。原图执行器、状态检查与分析器保留在所有条件中。共同任务说明给出 app、平台、解释器、输入输出和外部观察预算，并明确记录对[原文张力](SOURCE_TENSIONS.zh.md)的统一处理。

所有输入文件记录实际读取情况，不能只算摆在目录里的说明长度。缓存输入、未缓存输入、生成、工具调用、墙钟与设备占用分别保存；采用统一计价快照时，注明价格日期和币种。代理实际阅读文档、读取源码和运行工具的开销都计入，不用文档 token 数直接代替总成本。

观察截止时保留全部队列项及状态，区分完成、预算中止、参考失败、候选失败与工具故障。失败运行成本也计入。没有正确有效交付时，不造一个“单位成功成本”；可报告总花费和成功比例。

## 第一问：增加要求

从原文核对单中选择有明确来源的要求组，在共同任务基础上逐组加入。分目录说明、代码例子和记录模板会重复传递要求，必须一起登记。只删根文件的一段，却仍提供重复传达该要求的分目录文件，不能称作该要求的无规则条件。

先安排少量候选组合，保留每组实际改变的内容。分析针对这些具体要求组的增益，不把结果解释成内容无关的“规则越多越好/越差”。完成任务所需接口信息保留为共同基础；用哪些字段让规则间接重新进入，也要记录。

## 第二问：组织方式和成本

先比较完整原文与当前 Phase 4 整理稿。两者同为英文，三份分目录说明不变，区间外字节不变，代码例子和完成检查的原始标题保留。候选运行前完成逐项语义核对；解释不清的删改先回退。

另可准备仅排版版，保留全部词序、措辞和代码块，用于区分排版变化与合并重复内容。按需加载方案需要额外规定可见索引、读取决策和计费方式；先保留每次读取轨迹，再评估它究竟节省了多少。

## 第三问：遗漏

同一个要求在多个材料中出现，汇总时归为一个核对单元，另外记录重复次数和位置。给定条件下没有提出的要求不算违规；仍可比较共同交付的正确性和实用性。

核对至少区分适用、执行到、漏掉、有反证、当前证据不足。R21 的十种方案既有数目门槛，也有“确实不同”的语义要求；R30 既有字段，也有图依据是否具体；R35/R36 既有组合条目，也有组合是否真实实现。分别记录两部分，避免一张十行表被算作充分探索。

从每次交付中审阅假设与结果如何衔接、失败原因是否有证据、哪些非量化要求被省略。隐去条件后审阅同样的证据包；审阅模型的判断须核查引用和具体代码。缺交付与文风差分开记录，不能替缺失正文编写文风评分。

## 第四问：文字与机制

以相同文档分别比较仅文字、实际写入边界、写入边界加独立交付检查。用同一组核对单元衡量新增机制管到什么；限制或拒绝本身也记录成本和后续行为。

权限重点覆盖 R13/R14、A01、I01、S01：参考与公共代码只读，工作区可写。实际被拒绝的写入尝试与最终文件清单分别保存。事后比对哈希只能发现变更，不能称作事前权限阻止。

独立检查优先覆盖真实运行证据、版本和输入绑定、孤儿进程、缺失或悬空记录、队列与结果对应。代理自写的 PASS 或 JSON 文件不充当独立执行证明；研究方直接运行并保存输出，保留失败和最后代码版本。

策略是否多样、图是否忠实、理由是否具体等仍需语义与数值证据。比较时同时报告机械检查检出的比例、独立执行发现的问题和审阅发现的问题，不用一个汇总绿灯代替全部质量。

## 冻结正式试验前需要的实物

先在目标硬件上让同一个顺序参考完整跑通，拿到适配器输入输出、进程回收和稳定时间戳；完成一份图转换的数值验证。再据实确定每次观察预算、样本安排和受支持的策略空间。确认机制确实能阻止对应操作或拒绝无证据交付后，再冻结清单。

现成大型应用与新增轻量原生应用的来源和结论范围须分开。CPU 图检查实测用于确认原有机制边界，不能代替这里要求的完整参考运行。
