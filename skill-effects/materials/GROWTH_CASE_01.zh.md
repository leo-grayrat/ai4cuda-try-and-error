# 第一轮：失败之后实际补写了什么

这是一段本研究构建的追加历史，输入是开发题 AXPBY 的真实事件和最后源码。原始 CUDA Agent 文档为 376 行。模型针对这次失败补写了 34 行，合并后的文件为 411 行。完整追加内容、生成请求和用量在 `evidence/growth-01/`，不是从 FlashRT 作者历史恢复的内容。

## 触发事件

在开发运行 `dev-axpby-original-01` 中，模型第 20 号请求（从 0 开始计数）调用的正确性验证和计时均成功。此后它继续修改，最终 binding 使用了 `at::detail::empty_cuda`，独立编译报告 C2039 和 C3861。最后一次修改还给 ModelNew 加了 `__call__ = forward`。运行到 24 次请求上限，没有提交完成；最终文件未通过编译。

已由成功写入事件重建验证通过时与最后版本两套源码，放在 `evidence/development-original-01/`。其 timeline 和编译错误摘录带原始事件、日志的哈希。运行器在这次开发期间仍有编译反馈截断问题，故此记录用于开发和规则生成，不作条件效果比较。

## 追加的内容

模型分四组追加：安全分配接口、最终验证顺序、ModelNew 封装语义，以及工具使用。新增内容中同时出现了几种性质不同的条目：

- **针对本次错误的补充。** 明确禁止用 `at::detail::empty_cuda` 等版本私有接口代替已有分配路径，并要求按报错修改 binding。
- **对已有规则的再次强调。** 再说一遍构造签名兼容、Python 侧只做分配与扩展调用、最后要编译和验证。对应原清单 C03、C14、C16、C22 等，不能全算作新的独立要求。
- **把同一个意思拆成多条。** “最后文件必须是验证过的版本”“验证后写入会使旧结果失效”“不要停在最后一次写入”“早先编译成功不能抵消后来失败”“清理也算修改”，均围绕最后版本需要重新验证展开。
- **与原文存在需要审阅的张力。** 原文鼓励修复优化后的版本、不要回退到慢版本；补写内容要求保留或恢复已验证版本。何时继续修、何时恢复，受到外部预算和具体故障的影响。原文和追加内容都保留，评分前明确冲突与适用解释。
- **对执行环境的补充。** 追加正确的工具参数形式，并区分编译错误与传输、编码故障。其中把格式错误与传输故障一起叫作 tooling issues，可能淡化模型自己传错参数的责任，需要单独记录。

这一步已经重现了“遇到一次失败，就追加一串告诫”的过程。它是否使下一次任务做得更好，仍需对同一批保留题进行对照；条目增长、重复和成本都已能够实际追踪。

## 维护成本

首次为生成新增规则提供 8,192 个生成 token，全部用于 API 返回的推理量，未产生可用正文，结束原因为 length。第二次保留原请求内容、提高上限到 32,768，实际使用 8,677 个生成 token，其中推理量 7,761。第二次成功输出上述 34 行。

两次尝试都计入维护成本。失败尝试不被删除，也不把内部推理冒充最终文档内容。规则维护成本与后续每次任务读取、执行文档的成本分开记录，最后再说明不同复用次数下如何摊销。
