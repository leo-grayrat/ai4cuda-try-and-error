# 第四次追加：解释如何变成规则

这次开发使用 480 行累积文档，任务为 RMSNorm。模型在 54 次请求后提交，最后版本的编译、独立正确性与计时通过。维护模型随后增加 28 行，文档达到 509 行。完整追加与维护输入保存在 `evidence/growth-04/`，提交报告与最后源码保存在 `evidence/development-rmsnorm-growth02/`。

这轮有一个需要追踪的传播过程。提交报告写道：

> The GPU flips between two clock states that scale *all* columns by ~2×

维护模型接着在第 23 节写入：

> Absolute candidate latencies in this environment can change by roughly 2× between runs as GPU clock state changes.

计时记录支持不同调用之间存在波动；本轮计时工具没有采集 GPU 时钟、功耗或温度，因此不能据此确定波动由两个时钟状态造成。报告中的原因解释没有经过确认，追加文档却把它写成了环境事实。同一节建议在同一调用内比较候选与基线，这条测量建议可以另作判断，不必与未经确认的原因解释捆在一起。

这个例子暂时说明了规则形成过程中的一项风险：维护模型会把执行模型对失败或波动的解释带入下一轮要求。它还不能说明后续任务受到了多大影响，保留题对照仍需实际测量。原始追加不作人工修正，以保留这条传播路径；规则映射分别标记“可观察现象”“未经确认的原因”“新增行动要求”，不把同一段文字统称为已经证实的经验。

追加还重申了最后文件修改后的验证顺序，并补充向量归约中每个 lane 独立累加的要求。这些内容需分别核对适用范围、既有同义条目和新信息，不能将新增 28 行直接计成新增 28 项要求。
