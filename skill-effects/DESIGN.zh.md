# CUDA Agent skill 效果测试：设计与执行约定

日期：2026-10-19。用户提出四个问题并授权设计、调查和实验。下述样本量、任务和技术选择由本轮研究者提出，执行中保留修订记录。

## 要回答的问题

研究的起点是用户指出的真实使用问题：AI 每遇到一个失败，就在说明文档中补写一条“不要做什么”“必须做什么”，不断追加，积成几千行。规则与例外越来越多，阅读和执行越来越困难，遗漏也可能增加。**压缩是由累积失效引出的后续思考。** 因此主研究顺序是追踪累积过程、观察表现和成本，再比较压缩与权限、检查器如何处理同一批要求。不能将课题收缩为一个固定短文档与长文档的比较。

在同一模型、同一 CUDA C++ 扩展任务和相同资源上限下，增加文档规则，是否让实际交付变好？改进是否值得额外的输入、推理、生成和工具执行成本？规则增加后，哪些要求被遗漏？对反复强调的要求，权限和检查器是否比继续写提醒有效？

研究对象固定为 CUDA Agent 的真实开发流程：`kernels/*.cu`、配套 `_binding.cpp`、`model_new.py`、固定绑定注册机制，以及编译、验证、与 `torch.compile` 比较。原始 skill 已按提交 `473025c8af7878e928525138b5cb327d6bcdf9dd` 冻结，原文、基础设施和来源记录在 `sources/`。旧目录的 399 token 自写提示不作为“完整 skill”。

## 先解决环境，再封存正式实验

本机 Windows 已有 RTX 5060 Laptop、CUDA Toolkit 12.9、MSVC、PyTorch 2.11.0+cu128；两套现有 WSL 均未安装 PyTorch 或 nvcc。先验证现有 Windows 能否执行真实 CUDA C++ 扩展和 `torch.compile`，不为兼容性改用 Triton 候选。Windows 适配仅限编译参数、动态库后缀和命令入口；所有条件收到同一份平台说明，原始 skill 保持原样并另列其 Linux 命令的等价入口。若适配改变了任务语义，记录并重新设计。

开发用题为 CUDA Agent 原仓库自带 AXPBY。正式任务从公开 KernelBench 原始模型中选择四题，覆盖逐元素、归约、带参数归一化和多算子融合；冻结前实测显存、编译和基线。正式任务不以试验条件结果优劣筛选。每题原始形状之外，独立评测增加非整块尺寸、不同随机种子、非默认 CUDA stream 和重复调用，提前封存具体输入。任何形状缩减与原因必须留档。

## 对照条件

### 主实验：遇到问题就加规则

建立和公开一份追加记录：每次开发失败对应哪条原始要求、AI 为此补了什么、补到文档什么位置、是否已有同义规则、是否添加了例外或冲突。生成规则的开发任务与效果测量的保留任务分开，避免把刚看到的答案写入规则后在同一题上打分。追加过程只读开发失败和当前文档，不读取保留任务结果。

文档在预先指定的追加批次后冻结快照，同一批保留任务从空白会话分别使用这些快照。比较初始文档、追加后原文、保持同样要求的去重压缩版；权限和检查器也取自这一批要求。这样可以分别问：新规则是否修复了对应失败，旧规则是否被挤掉，真正新增的要求与重复告诫各占多少，以及长文档是否使说明质量下降。

几千行是需要覆盖的实际规模。优先从历史开发记录中找累积文档与追加过程；可取得的历史不足时，按上述开发失败驱动的过程构建并标注为本研究生成的文档，保存全部生成轨迹。必须分别记录行数、token、独立要求数和重复次数。扩展至 1,000 行和 3,000 行以上的压力条件不能靠空行凑数；若通过复述已有要求达到这一长度，它测量的是重复告诫的膨胀，不能记作新增几千项独立要求。累积主实验的批次、实际规则材料和样本量需在开发阶段完成后、查看保留任务结果之前封存。

每个增长阶段都保存原始追加文档及同要求压缩版，而非只在最终阶段做一次长短对比。对早期、中期和最高负荷三个阶段另做等长度背景文字对照。文档顺序保留真实追加顺序，并在选定阶段轮换新旧规则的位置，检查是否只是文末更容易被记住。

### 锚点对照：真实 CUDA Agent skill

以下对照保留为领域锚点和成分分析。原始 skill 约 339 行，它本身不能替代上述几千行累积文档的研究。原定 84 次及机制 48 次是此锚点实验的计划数，不是全项目的完成标准；正式预算统一在累积材料准备后封存。

首先把真实 skill 拆成逐条有来源的规则清单，注明适用条件、是否与基础任务契约重叠、观察方法。任务接口、成功定义和平台命令对全部条件相同；不能把全套 skill 偷放进“无额外 skill”的任务描述。

| 条件 | 给模型的额外文档 | 主要用途 |
| --- | --- | --- |
| bare | 无额外 skill | 同接口的实际基线 |
| core | 从原文抽出的限制和工作区规则 | 最少可操作规则 |
| workflow | core 加原文工作流程、迭代和证据要求 | 增加规则的收益 |
| condensed | 覆盖原文全部适用要求、去掉重复和示例 | 原规则集合的短版 |
| original | 冻结的原始 skill 全文 | 真实长文档的表现 |
| repeated | original 加原文已有关键限制的三次重申 | 重复强调是否有用 |
| length_control | condensed 加非指令性 CUDA 背景，长度匹配 original | 分开规则数量与文本长度 |

core、workflow、condensed 的规则都是原文的子集或压缩，逐项对照；不得另写一批更容易通过的规则。原始 skill 内的条件性建议按是否适用评分，例如本题无 GEMM 时不要求使用 Tensor Core。示例之间含混之处（例如禁止 torch C++ 运算同时允许内存分配）按原文用途解释并公开。

主实验四题，每条件三次独立重复，共 84 次，按任务和重复编号分块随机交错，固定随机种子。每次全新工作目录、独立会话、相同工具列表，GPU 串行运行。开发试跑另存，不进入正式统计。正式运行前冻结模型标识、温度、步数、单次请求及任务总用量上限、超时和工具输出截断策略；任何超过预算的结果保留并按预定规则处理，不能只分析成功完成的轨迹。

## 权限和检查器

沿用同一真实任务，比较 original 和 repeated 的文档条件，并分别加入两个机制：写入工具拒绝修改固定基础设施；结束检查器逐条检查可核验要求，反馈具体违例并允许模型在原预算内修正。主实验两种纯文档条件可复用，另跑四个组合，即四题乘三次乘四个附加条件，共 48 次。权限单独和权限加检查器分开，避免把二者混为一谈。

执行层不能让模型通过任意 shell 绕过文件权限。若现成 agent 无法提供真实受限工具，则使用透明且统一的模型工具循环，全部条件都通过同一组读、写、编译、验证、计时工具；只切换写入拒绝和结束门槛。记录拒绝请求、误拒绝合法修改、检查器运行时间及返工成本。代码检查器先用刻意违规和合法实现验证；不能把关键词未出现直接当成语义合规。

## 质量与成本

所有运行都由工作目录外的评测独立编译和验证，检查源码完整性、实际 CUDA kernel 启动及 GPU 计算。正确性先于性能。计时在预热后交错测量参考与候选，保存原始样本；报告 eager 和 `torch.compile` 两种基线，按原 skill 的候选延迟不超过 compiled baseline 的 0.95 计算最低目标达成率。所有失败和超时进入分母。

规则遵守既报告逐条通过率，也报告同一次交付是否满足全部适用要求。规则越来越多时，另外始终比较同一组共同规则，避免仅因分母增大得出“记忆变差”。区分文件权限、计算限制、工作流程、证据、解释完整性与文风。每项非量化要求都须回指追加记录中的原话和加入阶段，再制定正反例及适用范围；包括真实记录中出现的连贯解释、完整句子、避免短句信息堆叠等要求。尚未加入该要求的阶段不记作违例，同时可用同一盲审尺度记录交付质量本身。原始 skill 的事先预期、测量变化解释和实证结论，作为另列的证据说明维度。审阅引用原文证据，不靠字数或是否出现标题评分。先隐藏条件身份再审阅，并保留争议项。

输入 token 分未缓存、缓存读取和缓存写入，输出分正文及可取得的推理量；同时报告请求数、工具执行时间、GPU 时间和墙钟时间。API 未提供推理细项时如实记录字段。按运行时官方价格或供应商账单计算费用，价格和日期存档；没有可验证价格时直接使用各类 token，不杜撰美元成本。

收益抵不抵成本通过质量与成本的联合表判断，报告每个正确交付、每个达标交付的总消耗，以及不同预算下的成功率。不给正确率、速度和文风随意加权。按任务配对报告差值和不确定区间，只有四道任务时明确列出每道题结果；不把重复采样当成很多独立任务。
