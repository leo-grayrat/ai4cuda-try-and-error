# Open Coding Result — GPU Kernel 优化 diff 的程序变换归纳

独立开放编码员产出。输入仅为 `data/probe_edges/manifest.json` 与 24 个 `.diff` 文件，
未读取任何含预设分类体系的文件。每条边先写一句"实质做了什么"，再聚类。
编码方式：**每条边给一个主编码（primary）+ 若干伴随编码（secondary）**，
因为多数边同时携带 2–4 种变换；主编码取"对加速贡献最大 / 改动结构上最承重"的那一个。

标注 `truncated: true` 的边只看到 diff 的前半部分（文件末尾 `...[TRUNCATED]`），
其记录中已注明"部分可见"，判断只基于可见 hunk。

## C. 无法归类的边

**没有完全无法归类的边**，但有 4 条需要标注归类的不可靠性，属于"勉强归类"：

1. `L2_2_57_150_151` → **G（单例支撑一个类别）**
   它只有两个 hunk：autotune 列表 + `clone()→empty_like()`。若把 G 并进 F（都属"消除不必要运行时开销"），
   类别数可降到 6；我保留 G 是因为"删一次显存拷贝"与"把计算提前/缓存起来"在程序变换空间里
   是可分离的两个动作（前者改内存分配语句，后者改执行时机/作用域）。
   归类风险：1.330 的加速里，有多少来自 `clone` 删除、多少来自新增的 `BLOCK=8192` 候选，从 diff 无法区分。

2. `L2_2_9_17_50` → **主编码在 C 与 B 之间不可判**
   同一条 diff 里，代数折叠（消掉 3 个逐元素算子）、精度切换（fp32→fp16 + TF32）、后端搬家
   （GEMM 交回 cuBLAS）三件事互相耦合，任何一个单独存在都可能拿到大部分 5.02x 收益。
   我按"结构性改动最承重、且必须先于其他两步才成立"选了 C，但这属于编者判断而非 diff 证据。

3. `L2_2_69_85_93`（18.33x，全场最高）→ 归 F，但语义可疑
   该边唯一改动是删掉运行期计时搜索，核函数体一字未动。它能拿到 18 倍"加速"
   强烈暗示 measured time 里包含了搜索本身（即父版本把 autotune 放进了被计时的 forward）。
   也就是说，这条边测量的可能不是"程序变换带来的性能提升"，而是"把测量污染清出去"。
   开放编码时我仍按结构归 F，但会额外标注：**它的加速标签与其他边不可直接比较**。

4. `L2_2_3_52_151` / `L2_2_4_73_74` / `L2_2_7_122_124` → "回退型改动"方向性模糊
   三条边都是把父版本某项已施加的优化**撤掉**（拆掉融合核、撤掉 fp16、撤掉 fp16+夹紧），
   同时补上另一项。它们的形式动作与"施加优化"完全相反，若分类体系按方向命名就会无处安放；
   我按"改变了什么可观测对象"归类（D/B/C），不把"回退"当独立属性。

## D. 归纳时最难划清界限的地方

最尖锐的一条边界是 **A（工作划分/布局重映射）与 D（流水段重构）**。
`L2_2_91_3_28` 同时做了两件事：把"一行一 program"改成"ROWS_PER_PROG 行一 program"（明显的 A），
又把"三趟扫描 max / sum / write"改成"两趟 + online 合并递推"（明显的 D）。
我的切分标准是：**A 只改"同一套算子分给谁执行"，D 改"算子被执行几次、跨几段"**。
一旦某条边引入新的递推关系（online softmax 的 `running_max/running_sum` 合并公式），
它就不只是重新分工，而是真的改变了计算过程，此时 D 优先。这条规则勉强可用，但需要人为规定——
`L3_3_29_46_52`（第二趟重新载入 A、B 而不是读中间缓冲）同样卡在"这是取消一次物化（D），
还是改变每趟的取数方式（A）"的缝上，我选了 D，因为 diff 明确删掉了一个全局缓冲的 store/load 对。

第二条难界是 **B（精度制度）与 C（代数改写）**。
`L2_2_7_122_124` 把第二次 sigmoid 换成 softsign，这是"用便宜算子替换贵算子"（C），
但同一条边又把 fp16 全撤回 fp32（B）；`L2_2_94_130_142` 的 `where(v>20, v, log(1+exp(v)))`
是纯数值稳定性改写，既不动精度也不动并行度，硬要归 C 就得允许"C 包含只为安全而不是为省算子的改写"。
我最终的临时判据是：**若改动可以只用"等价的数学/近似式替换"描述而不提及 dtype，归 C；
若改动必须提及 dtype 或 `allow_tf32` 才说得清，归 B。** 这个判据对 `L2_2_4_73_74` 就失效了——
它把带 `EXP_CLAMP=11` 的 fp16 夹紧式换成 `where(x>0, …)` 分支式，
dtype 回退与公式重写被作者绑成一次动作，diff 层面无法拆解，我只能声明主编码 B、把 C 记为伴随。

第三条难界是 **E（后端搬家）与 F/B 的纠缠**，且暴露了本样本一个更麻烦的现象：**存在成对的互为反向的边**。
`L3_3_46_94_95` 把自研 Triton BMM 删掉换成 `torch.bmm` + autocast（自定义核 → 厂商库）；
`L3_3_49_95_96` 把 PyTorch 分块实现换回一个手写 Triton scan 核（厂商库 → 自定义核）。
两条都被记录为"成功优化"、都有可观加速（4.36x、8.26x）。如果我的分类体系里只放
"用库替换自研核"或"用自研核替换库"中的一个动作，必然有另一条无处安放。
这提示 E 应被编码成**一个有方向的双值属性（library ⇄ custom kernel）**，
而不是"引入 kernel"这一单向类别。同理，B 必须允许 fp32→fp16 与 fp16→fp32 双向，
D 必须允许"合并核"与"拆分核"双向，A 必须允许"扁平化"与"二维分块"双向——
我在每条定义里都刻意写成了双向措辞，这是本次开放编码最主要的规则设计决定。

最后一个贯穿性问题：**几乎所有边都是多动作包（bundle），单条 diff 内部各动作的贡献不可分**。
24 条边里只有 `L2_2_69_85_93` 与 `L2_2_57_150_151` 勉强算"两动作"，其余平均携带 2.7 个可辨识变换。
因此"主编码"本身是我按结构显著性强加的排序，不是从数据里读出来的；
若换一位开放编码员，`L2_2_9_17_50` 很可能被主编码为 B、`L3_3_17_10_11` 很可能被主编码为 F（宿主循环合并）。
我在表格里保留 secondary 列，正是为了让后续控制实验能检验：
用主编码计算的类别分布，与把 secondary 也算进来的分布，差异有多大。
