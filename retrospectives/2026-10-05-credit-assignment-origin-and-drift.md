明白，而且我现在觉得：**是的，确实偏移了，而且偏移得还不小。**

你最开始那个想法，其实比后来这套“program transformation action space”要直接得多。

CUDA Agent 训练时，Actor 仍然是一 token 一 token 地生成；价值模型（Critic）也沿着这条 token 序列，在每个时间步估一个价值，再通过 GAE/PPO 得到每个 token 对应的 advantage。也就是说，最后 kernel 跑出来到底值多少，训练时仍然要沿着几千、几万甚至更长的 token 序列往回分配。

而你最开始的违和感是：

> **程序性能真正发生变化，显然经常不是因为某一个 token。**
>
> 真正有意义的是“这次把两段计算融合了”“这里把中间写回去掉了”“这里改变了每线程工作量”“这里换了精度/布局/归约方式”这样的代码决策。
>
> 那为什么价值模型的基本评价单位还必须是 token？

所以最原始的问题其实是：

\[
\boxed{\text{价值到底应该分给 token，还是分给程序级决策？}}
\]

这个问题直接咬的是 **Critic 怎么判断价值、advantage 怎么分配、Actor 最后根据什么信号更新**。

---

后来我们发生了一次很关键的转弯。

我们开始说：

> 既然真正有意义的是程序动作，那干脆让 Agent 的 action 本身就变成 `Fuse(...)`、`Tile(...)`、`IncreaseWorkPerThread(...)`。

这已经从：

> **“训练信用应该落在哪个单位上？”**

变成了：

> **“Agent 应该在哪种动作空间里搜索？”**

二者当然相关，但不是一件事。

你完全可以保持现在的生成方式：

> LLM 还是自由生成整段 CUDA/Triton 代码。

然后在训练时，把这一大段 token 中属于同一个程序决策的部分识别出来，把它们视为一个单位，让 Critic 判断：

> “执行这个决策之前，当前程序价值是多少；执行完这个决策之后，价值变成多少。”

这样你根本不用先强迫模型输出某个 DSL 或从菜单里选择 `Fuse`。

这其实更接近你最开始的想法。

---

而 Qwen 这次做的事情，几乎全跑去了另一个问题：

> “过去这些成功 diff 能不能归进一套 transformation vocabulary？”

它研究的是：

> 这些代码改动能不能被描述成 Fuse、PrecisionChange、Tile……？

于是我们又讨论：

- 词表能不能覆盖；
- `Other` 多不多；
- 类别会不会跨任务出现；
- 同一种类别代码长得是不是不同；
- Triton 下哪些类别不可见；
- backend choice 算不算一种 action；
- autotune 和结构修改是不是混在一起……

这些事情最多只回答：

> **“程序级动作这种描述单位有没有可能存在？”**

它们完全没有触及你最初最关心的那一刀：

> **如果我真的把这些动作识别出来，Critic 能不能因此更准确地评价它们？Actor 能不能因此学得更好？**

所以你现在觉得“怎么越研究越和价值模型没关系了”，这个感觉是对的。

---

甚至可以更严格地把我们目前的路线拆成三层。

第一层是：

> **代码里到底有没有可以被识别出来的程序决策？**

比如一大段 diff 里，能不能说“这部分整体是在做 fusion”。

Qwen 只碰了这一层，而且还是很粗的观察。

第二层才是你真正开始感兴趣的：

> **如果能识别程序决策，价值模型能不能直接评价这个决策？**

举个最简单的抽象例子。

原来是：

```text
token1 -> V1
token2 -> V2
token3 -> V3
...
token800 -> V800
```

其中 token 1 到 token 800 合在一起，其实只是完成了：

> “把 producer 和 consumer 融合。”

你真正想问的是：

```text
程序状态 P
    ↓
Fuse(A, B)
    ↓
程序状态 P'
```

那能不能直接学：

\[
V(P)
\]

以及：

\[
Q(P,\text{Fuse}(A,B))
\]

或者至少给这一个完整动作一个 advantage，而不是硬把 credit 撒回那 800 个 token。

**这一层我们现在基本没做。**

第三层才是最终问题：

> **这样训练以后到底有没有比 token-level PPO 学得更快、更稳、更有效？**

这一层更是一点都没碰。

---

所以现在回头看，Qwen 那次 Auto-Research 最大的问题之一，就是把第一层搞得特别热闹，以至于看起来像是在推进整个方向。

但事实上：

\[
\text{找到一些可以命名的程序动作}
\]

距离

\[
\text{用这些动作做 value / advantage assignment}
\]

中间还有非常大的一步。

而

\[
\text{action-level credit assignment}
\]

距离

\[
\text{训练性能真的提高}
\]

又还有一步。

我们当前其实只是站在第一步前半截。

---

而且还有一个更尖锐的问题。

我们之前说：

> “55 条成功 edge 可以被归成少数类别。”

即便这个结论完全是真的，它也**不自动说明这些类别就是 Critic 应该评价的单位**。

因为 Critic 真正需要的是：

> 哪一个决策改变了未来的回报？

而 taxonomy 只是在说：

> 这段代码在人类看来属于什么类型。

这两个完全可能错位。

例如一个 child 一口气：

- Fuse；
- 改 precision；
- 改 autotune；
- 换 launch config。

我们可以给它贴四个漂亮标签。

但 Critic 真正想知道的是：

> 到底是其中哪个决策让最终 reward 从 2 变成 3？

或者：

> 这些动作是不是必须组合起来才有效？

这才是信用分配。

所以从这个角度看，Qwen 后面那些 `Fuse 17 次`、`PrecisionChange 15 次`，对最初问题其实只有非常弱的帮助。

它只告诉我们：

> “也许存在可以讨论的中间单位。”

没有告诉我们：

> “这些单位是正确的 credit 单位。”

---

我甚至觉得，我们应该承认一个更早的偏移点：

不是 Qwen 才开始偏。

**当我们第一次把问题改写成“Program Transformation Action Space”时，方向已经发生了一次实质变化。**

最初是：

> token-level credit assignment 可能太细。

后来被我们改写成：

> token-level action space 可能错了。

这两个句子长得很像，所以很容易觉得只是重新表述。

其实不一样。

前者允许：

> **生成仍然是 token，学习信用按程序动作来算。**

后者更容易走向：

> **连生成接口也改成程序动作。**

后者是一个更强、更大的主张。

Qwen 就顺着这个更大的主张一直研究下去了。

于是我们原本盯着 CUDA Agent 的 Critic/GAE，最后开始研究 transformation taxonomy。

你现在觉得脱节，就是因为这个逻辑分叉终于显出来了。

---

所以如果现在把主线重新拉直，我认为最准确的版本应该是：

> **CUDA Agent 的性能奖励最终来自整个程序执行，但 PPO 的学习信号落在 token 时间步上。程序优化往往由少数程序级决策造成，因此值得研究：能否识别这些决策，并把价值估计与信用分配提升到决策层，而不是 token 层。**

这才是你最初那个 idea。

至于：

> “进一步把这些决策直接变成 Agent 的显式 action space”

可以保留，但应该是**后续更激进的一个分支**。

而不是反过来让它取代原问题。

所以答案就是：**是，偏移了。Qwen 那次工作最多是在给“是否存在可用的程序级信用单位”做非常前置、很弱的摸底，并没有真正研究价值模型，也没有研究训练信用。我们之前把它讲得像是在直接推进核心问题，确实说重了。**
