# CUDA 代码决策与性能信用：冻结的实验约定

版本：2026-09-25，首轮新 GPU 测量前。后续改动须另起版本并说明原因；已经看过结果的案例不能因修订约定而变成留出案例。

## 要回答的三个问题

1. 真实父子代码中的提速能否归到可说明的程序决策，例如减少拷贝、改变并行布局或融合计算？一个决策可包含多处相互依赖的代码。
2. 在有限的正确性与对照计时预算内，能否比直接看文本差异更可靠地找到这些决策？
3. 若前两点成立，把同一份性能奖励分给产生决策的生成内容，是否改善留出任务上的正确性和有效提速？

这三个问题分别报告。工具能生成候选、测试通过或单例提速，均不自动回答后一个问题。

## 按固定顺序筛查新案例

数据源先使用本地 SHA-256 为 `14e31f73af3491cff486ce25f08c48e08f0a042816539abe3bb9541841b39cc5` 的 AdaExplore Level 2 归档。只取显式父边、归档标记父子正确、同一设备编号且源码不同的修改；归档计时不用于排序。按任务编号、子节点编号、父节点编号升序排列。把完整候选表及归档筛除原因保存后，再开始本机筛查。已经查看过的案例标为开发案例，不可进入留出集。

每个候选都记录 `task / parent / child`、源码哈希、归档状态、本机父子正确性、筛除原因、任务类别及查看时间。先从题目参考实现确定逐元素、归约或矩阵/块计算类别；归属不清记 `other`，不得为了凑数改变类别。进入主要分析的案例还需有至少两处可执行代码变化；单处变化可作为计时或映射检查。父子有一方在本机错误时保留记录并停止该边的性能归因。

先争取三类各 3 条本机有效的困难修改，再争取至少 30 条。扩展前按任务编号锁定开发/留出划分，同一题的全部版本只在一边。样本不足时报告筛查数量和原因；不手造“真实 Agent 修改”来补足。

## 测量前先写动作假设

在看该边的撤销计时前，记录：动作名称、预期改变的运行机制、父子代码位置、必需的连接/依赖代码、预期速度方向、不能拆分的理由。一次优化决策可横跨多个差异块。普通对照须优先选可执行代码改动，不能默认用注释或文档。若没有可信的普通可执行对照，记录 `no_executable_control`。

每边最多选择 3 个动作和 1 个普通代码对照构造撤销或单独保留版本。保存测量前的原文与文件哈希；测量后若发现动作边界有误，新增修订记录，不覆盖原判断。自动方法的预测也必须在对应测量前封存。被测案例的规则补丁不能倒灌为该案例的“事前预测”。

## 正确性与计时

复用本仓库 `lab.py run` 的 KernelBench 入口，不另写评测器。固定参考题、工作量、源码和本机 GPU；保存每个候选源码哈希、上游评测器版本、设备 UUID、正确性和原始计时。先测父子正确性，再测构造版本正确性；只有父子和对应构造版本都正确，才比较性能。

每个可比较案例至少做 3 轮不同顺序种子的重复计时，沿用现有每候选 5 次正确性检查、30 次计时。令 `T_child` 为子版本延迟、`T_without` 为撤销动作后的延迟；报告每轮 `log(T_without/T_child)` 及中位数。正值表示该动作在**当前子版本上下文**中有帮助，不宣称它独占父子速度差。逐轮方向不一致，或效应与同期普通对照波动相当，标为 `inconclusive`。撤销错误标为 `invalid_reversion`；无法独立拆开的依赖标为 `joint_action`，共同测量。

`2_20` 先复查现有手工版本的源码和依赖关系，封存测量前的动作假设，再按上述流程运行。它的结果留在开发集。

## 方法比较与进入训练的门槛

开发集允许探索动作分组的实现，但进入留出集前只冻结一个待检验方法。比较对象包括直接文本差异、差异分块、`e42d675` 的旧规则和冻结的新方法；所有方法获得相同题目、父子代码和最多 3 个动作提议预算。差异分块基线若只借鉴 DiDPO 的分块思想，报告时不得称为完整复现 DiDPO。

逐任务报告：前三个提议覆盖了多少得到实测支持的动作，误报了多少普通可执行改动，是否遗漏共同动作的依赖代码，额外评测了多少候选，以及不可判定比例。只在按任务留出的困难案例上判断优劣；旧案例仅用于开发和例示。若代码优先方法在相同预算下没有稳定超过简单差异基线，或代价抵消收益，停止在归因结果。留出案例不能反复用于修方法；下一轮研究必须另设留出任务。

## 生成内容映射和学习对照

学习数据另采集短生成轨迹，保存原始回复、生成时 token ID 和偏移、应用前后源码。只有能够唯一对应到真实生成内容的动作才有动作级性能信用；删除、应用时改写、位置冲突均保持未映射。先报告映射覆盖率和未映射原因，再决定能否训练。公开归档不得补造 token。

训练预检固定同一个本机可运行的初始生成模型、任务、更新方法和总生成/评测预算；如果 8 GB GPU 无法运行，或正确修改与可靠映射不足，记录为可行性失败，不宣称信用分配失败。预检通过才比较整段共享、差异分块、实测动作三种分配。三组输入轨迹、正确性奖惩及每条回复的性能奖励**总量相同**；只改变性能部分落到哪些真实生成位置。共同动作一起分配；多个撤销效应不能累加创造额外奖励。训练与 GPU 计时分开运行，留出任务报告正确率、有效提速比例、评测成本和多次运行的波动。

## 记录与变更纪律

每条记录需能追到：任务及父子源码 → 测量前动作假设 → 构造版本及正确性 → 各轮原始计时 → 判断状态 → 若有，原始回复及生成位置 → 奖励分配。原始记录放在忽略目录 `runs/`；入库的索引、代码哈希和结果报告指向这些本机记录。每阶段单独提交并说明“看到了什么、仍不能说明什么”。规则修补、工具通过测试或单例速度变化本身不算完成研究阶段。

本轮仅使用现有一块 GPU。早期 TF32 与 2×2 案例继续作核查，不主导研究问题；跨 GPU 泛化待有第二台设备再议。
